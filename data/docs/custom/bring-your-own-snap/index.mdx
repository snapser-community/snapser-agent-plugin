# Bring your Own Snap

Bring your own Snap to Snapser and make it part of your game or app kubernetes cluster.

## Concept

Snapser allows developers to bring their microservices, macroservices or monoliths to the Snapser platform. Developers can bring any number of microservices to the platform and they can be written in any language. Snapser CLI will be able to build your microservice and push it to your personal Snapser Container Registry. You will then be able to publish new versions of your service which your studio developers can deploy to their Snapend.

<Note>
  All your published BYOSnaps always remain private to your company. No one
  outside your studio can see or use your BYOSnaps.
</Note>

## Networking

### BYOSnap Accessibility

In order for your Snapend gateway to route calls to your BYOSnap, each API endpoint must have:

1. **An API Prefix** - typically `/v1` or `/v2` (set when you publish your Snap)
2. **Authentication Type Declaration** - specify which auth types your endpoint accepts

#### API Prefix

Each BYOSnap API endpoint should have a prefix to route calls from your Snapend gateway. 

BYOSnap URL format is as follows:

```bash
https://gateway.snapser.com/$clusterId/$prefix/$byosnap_sid
```

#### Authentication Headers

BYOSnaps use header-based authentication. Snapser automatically injects the appropriate headers based on the request context:

- **`Auth-Type`**: `user`, `api-key`, or `internal` - specifies how the request is authenticated
- **`User-Id`**: The ID of the user making the request (for user auth)
- **`Gateway`**: `internal` - indicates the call is from within the Snapend

Your BYOSnap validates these headers using the `validate_authorization` decorator/middleware.

<Note>
  See the [Authentication & SDK Categories guide](/docs/custom/bring-your-own-snap/byosnap-auth-and-sdk) for complete details on the authentication system and how to expose endpoints in different SDKs (including the Admin SDK).
</Note>

### Understanding Authentication Headers

Your BYOSnap code validates requests by checking the authentication headers Snapser injects. Here's what each header indicates:

1. **`Auth-Type: user`** - The request is from an authenticated user. The `User-Id` header contains their ID.
2. **`Auth-Type: api-key`** - The request is from a trusted server using an API key.
3. **`Auth-Type: internal`** - The request is from another Snap within the same Snapend (indicated by `Gateway: internal`).
4. **`User-Id: <id>`** - Present for user-authenticated requests; contains the validated user ID.
5. **`Gateway: internal`** - Set to `internal` for Snap-to-Snap calls within the Snapend.

Use your `validate_authorization` decorator/middleware to enforce the correct auth types on each endpoint. For complete details, see the [Authentication & SDK Categories guide](/docs/custom/bring-your-own-snap/byosnap-auth-and-sdk).

## Setup

### Snapctl Setup

Snapser provides a way to bring your custom code via the Snapser CLI tool.

#### Step 1: Generate a BYOSnap Profile

Generate a BYOSnap profile. This JSON file contains the name, description, platform, language, and multi environment configuration for your BYOSnap. We recommend that you commit this file to root of your codebase.

<Note>
  This file sets your BYOSnap's **template**. Every publish updates it, but a Snapend
  only picks it up at the moment the BYOSnap is added to that Snapend. Editing this
  file will not reconfigure a Snapend that already runs your snap. Read
  [Profile vs. Snapend Manifest](#profile-vs-snapend-manifest) before you rely on it
  to change CPU, secrets or env vars.
</Note>

<CodeGroup title="BYOSnap Profile Generation" tag="bash">
```bash
# Command to generate BYOSnap Profile.
# $file_name = Profile file name. Extension should be with .json or .yaml or .yml. Eg: snapser-byosnap-profile.yaml
# $out_path = Path where the profile will be generated. Best practice is to generate the profile in the root of your codebase.

snapctl byosnap generate-profile --profile-filename $file_name --out-path $out_path

```
</CodeGroup>

The sample generated file will look like the following. You will need to fill in the TODOs.

<CodeGroup title="BYOSnap Profile" tag="snapser-byosnap-profile.json">

  The `hpa` field is **production only**. Leave it `null` to run with a static `min_replicas` count, or set it to an HPA template to enable autoscaling on the production deployment. A populated `hpa` looks like:

```json
"hpa": {
    "min_replicas": 3,
    "max_replicas": 50,
    "cpu_utilization_threshold": 75,
    "memory_utilization_threshold": 85,
    "scale_up": {
        "stabilization_window_seconds": 0,
        "period_seconds": 30,
        "percent": 100
    },
    "scale_down": {
        "stabilization_window_seconds": 600,
        "period_seconds": 60,
        "percent": 25
    }
}
```

Specify exactly one of `percent` or `pods` on each scale behavior. `scale_down.percent` must be strictly less than 100. See the [Profile Tool](/docs/custom/tools/profile-tool#autoscaler-production-tab) doc for the full field reference and bounds. Dev and Stage templates must always have `hpa: null` — the validator rejects HPA on non-prod templates.

</Note>

### Step 2: Build and Publish your BYOSnap

This step will create a new BYOSnap if not present, build your code, push it to your Snapser registry and publish it as a new version.

<CodeGroup title="BYOSnap Publish" tag="bash">
```bash
# Command to publish BYOSnap.
# $byosnap_id = BYOSnap ID for your snap. It should be starting with byosnap-. This is to avoid any collisions.
# $version = Semantic version for your snap Eg: v0.0.1
# $path = Local code path where your Dockerfile is present
# snapctl byosnap publish --byosnap-id byosnap-jinks-flask --version "v0.0.1" --path /Users/AJ/Development/SnapserEngine/jinks_flask

snapctl byosnap publish --byosnap-id $byosnap_id --version $version --path $path
```

After this step, your BYOSnap will be ready to be used in your Snapend.

#### Multi-Architecture Support
Snapser supports multi-architecture BYOSnaps. You can build and publish your BYOSnap for multiple architectures like `linux/amd64` and `linux/arm64`. Each published version can use a different architecture, allowing you to support different developer machines and environments.
<Note>
  You can use the `--platform` flag to the `snapctl byosnap publish` command to specify the architecture for your BYOSnap. The options are 'linux/amd64' or 'linux/arm64'. If no option, is given the platform uses the one in your BYOSnap profile.
</Note>

##### Readiness Configuration

You can also set the readiness configuration for your Snap. This includes:

1. Path - The full path to the readiness endpoint. For example, `/v1/byosnap-$byosnapId/healthz` or `/healthz`.
2. Start Delay - The time to wait before starting the readiness check. Typically you want to chose a number between 1-10 seconds.

<Note>
  The readiness endpoint is accessed by the Snapser internal system. Hence you
  do not need to expose the readiness endpoint to the outside world if you do
  not want to. Use the endpoint URL without the prefix to make it strictly
  internal eb: `/healthz`. But if you want to expose the readiness endpoint to
  the outside world, you can use the full URL with the prefix like
  `/v1/byosnap-$byosnapId/healthz`.
</Note>

##### BYOSnap Ingress Ports

Each BYOSnap allows you to expose ingress ports

1. External Port - This is the port your BYOSnap is listening on. Your gateway will use to route the calls to your Snap.

   - Name: Name for your external port. This is hardcoded to `http`
   - Port: The port your BYOSnap is listening on. Eg: 8080
     <Note>
       The BYOSnap admin tool built using the BYOSnap tool builder will use the
       external port to reach your BYOSnap endpoints.
     </Note>

2. Internal Ports - These are the ports your BYOSnap is listening on inside the container. Best used to expose a port so that other BYOSnaps can talk to your BYOSnap. You can have more than one internal port.
   - Name: Name for your internal port.
   - Port: The port your BYOSnap is listening on. Eg: 8080

<Note>
  It should be noted that the name and the port numbers need to be unique across
  external and internal ports.
</Note>

##### BYOSnap Version

You will need to provide the semantic version of your BYOSnap. If you have published a BYOSnap before, the
new BYOSnap will have to be a higher version than the previous one.

<Note>
  This is done to protect your infrastructure from breaking changes. Forcing new
  versions to be higher ensures that any live Snapends are not impacted by the
  new version.
</Note>

##### Multi Environment Configuration

You can also add your multi environment configurations. Which includes CPU, Memory, Min Replicas, Command, Arguments, Environment Variables, and (production only) an HPA block for
dev, stage and prod environments. You at least need to setup the configuration for one of the environment. You can always come back and add more configurations later.

1. CPU - The CPU limit for the Snap
2. Memory - The Memory limit for the Snap
3. Min Replicas - The minimum number of replicas for the Snap. The default is 1 in Dev and Staging and 2 in Prod. On Production, this is the **static** replica count — it only takes effect when HPA (see below) is disabled.
4. Environment Variables - The environment variables for the Snap you want to initialize with
5. Command & Arguments (optional) - Optional command and argument overrides.
6. HPA (optional, **production only**) - Horizontal Pod Autoscaler configuration. When enabled, the prod deployment scales between a min and max replica count based on CPU and memory utilization thresholds, with configurable scale-up and scale-down behaviors. When `hpa` is null, the static Min Replicas above governs. HPA must be `null` on Dev and Stage. You can also configure HPA per-snap during the **Promote-to-Prod** flow's Customize step.
7. Secrets (optional) - Up to 5 references into the [Secrets Manager](/docs/custom/tools/secrets-manager) per environment template. Each reference is a `(file_name, tag)` pair that Snapser mounts at `/opt/byosnap-secrets/$file_name` inside the pod at startup, with the tag's value as the file contents. Use this for API keys, certificates, JSON service-account blobs and anything else you don't want baked into the image. See the Secrets Manager doc for the full lifecycle.

<Warning>
  These per-environment values are the BYOSnap's **template**, not live settings. They
  are copied into a Snapend at the moment your BYOSnap is added to it, and never again.
  Editing them later — in the profile or here — reaches every Snapend that adds this
  BYOSnap *afterwards*, but none that already run it. For those, use
  **Customize Snapend**. See [Profile vs. Snapend Manifest](#profile-vs-snapend-manifest).
</Warning>

<Note>
  Once your BYOSnap is deployed to a Snapend, head to **Infrastructure → Dashboard** on that Snapend to verify what actually landed: CPU / memory, autoscaler (HPA) state, and the attached secrets / args / env vars for each BYOSnap, all sourced from the live snapend manifest.
</Note>

## Profile vs. Snapend Manifest

This is the single most common point of confusion with BYOSnaps, so it is worth
being explicit about it. In one sentence:

> **A BYOSnap profile is a template for adding the BYOSnap to a deployment. Once
> it's added, you manage the deployment profile — the Snapend manifest.**

### How it works

Think of your BYOSnap profile as a **recipe card**.

When you publish a BYOSnap, you hand Snapser that card. It says how much CPU your
service wants, which environment variables it needs, which secrets to mount — the
lot. Snapser files the card away.

Later you build a Snapend and say "add BYOSnap A to this." Snapser pulls out your
card, **copies** what's on it onto that Snapend's own sheet of paper, and from
then on it cooks from the sheet — not from the card. That copy happens exactly
once: the first time that particular BYOSnap lands on that particular Snapend.

Now say you change your mind. You add a secret to the card, bump the CPU, and
publish again. Snapser updates the filed card. **Any Snapend you build from here
on gets the new version**, because it takes a fresh copy at the moment you add
the snap.

But the Snapends that are *already* running your BYOSnap? They're cooking from
sheets they wrote a long time ago. Your new card never reaches them.

And here's the bit that catches almost everyone: telling one of those Snapends to
run a **newer version** of your BYOSnap doesn't help either. That swaps out the
code and nothing else. The sheet stays exactly as it was — same CPU, same env
vars, same secrets (or same lack of them).

So if you want a Snapend that's already running your snap to pick up a config
change, you have to go and edit its sheet directly. That's **Customize Snapend**
in the Web UI.

One more wrinkle, because it surprises people in the good direction: "already
running your snap" is per BYOSnap, not per Snapend. If you've got a Snapend
that's six months old but has *never* had BYOSnap A on it, adding A to it today
works like a brand-new Snapend — it takes a fresh copy of the card, secrets and
all.

**Rule of thumb:** if the Snapend has never seen this BYOSnap, the profile is in
charge. The moment it has, the Snapend is in charge, and the Web UI is how you
talk to it.

<Note>
  **Two different things get called a "profile".** Keep them apart:

  - **BYOSnap profile** — your `snapser-byosnap-profile.json`. A *template*. Lives in
    your repo, shipped to Snapser on publish.
  - **Deployment profile** — the BYOSnap's block inside a **Snapend manifest**. The
    live configuration for one BYOSnap on one Snapend. This is what actually gets
    deployed, and it's what **Customize Snapend** and the Promote-to-Prod Customize
    step edit.

  The first becomes the second, once, at attach time.
</Note>

<Warning>
  **Publishing a new version does not re-apply your template to Snapends that
  already run this BYOSnap.** Bumping a Snapend to a newer version rolls out new
  *code* — it does not re-read the template. To change CPU, memory, replicas, env
  vars, command, args, HPA or **secrets** on a Snapend that already has your
  BYOSnap, use **Customize Snapend**.
</Warning>

### Why they're separate

This split is deliberate, and once it clicks it's one of the nicer things about
running a BYOSnap.

Your **image** and your **runtime configuration** have completely different
lifecycles. Code changes when you ship a feature. CPU, replica counts, env vars
and secrets change when your traffic changes, when you rotate a credential, or
when someone is paging you at 2am. If those were welded together, every "give it
more memory" would mean editing a file in your repo, a Docker build, a new
semantic version, and a publish — just to change one number.

Because they're decoupled, they don't. Need to double the CPU on a Snapend? Open
**Customize Snapend**, change it, deploy. Same image, new configuration — no new
BYOSnap version, no rebuild, no repo change. Rotating a secret works the same
way: repoint the tag and deploy. (Production is the one exception, and for a
related reason — direct edits there are disabled, so production config changes go
through the **Promote to Prod → Customize BYOSnaps** step where they're reviewed
alongside the rest of the diff.)

It also means one published version can run everywhere at once with settings that
suit each place: 100 millicores and a test payment-provider key on an engineer's
dev Snapend, two cores with HPA and the live key on prod. One image, many
deployment profiles.

And it keeps live infrastructure out of reach of a repo edit. If profiles stayed
live, someone changing a default in a JSON file and publishing could silently
resize or reconfigure a running service. Instead, changing a running Snapend is
always an explicit action taken against that Snapend.

The trade-off is exactly what this page is about: your profile stops being the
source of truth the moment a Snapend has your snap. That is the price of your
repo not being able to reach into live infrastructure — and for live ops, it's a
good trade.

### When the template is applied

| Moment | What happens to the template |
| ------ | ---------------------------- |
| `snapctl byosnap publish` with an edited profile | The BYOSnap's **stored template is updated**. True on the first publish and every publish after it. |
| **BYOSnaps → \<your snap\> → Update** in the portal | Same thing — edits the stored template directly. |
| Adding the BYOSnap to a Snapend **for the first time** | The stored template is **copied into that Snapend's manifest**. This is the one and only handoff, and it happens whether the Snapend is brand new or has existed for months. |
| Bumping the version on a Snapend that already has this BYOSnap | **Nothing.** New image, same configuration. |
| Any later edit to the profile or stored template | **Nothing**, for any Snapend already carrying the BYOSnap. |

The two cases worth memorising:

1. **The Snapend does not have this BYOSnap yet.** Adding it pulls the current
   template as the defaults. From here on, that configuration is part of the
   Snapend manifest.
2. **The Snapend already has an earlier version of this BYOSnap.** Updating the
   version does *not* re-apply the template. Go to **Customize Snapend** in the
   Web UI and change what you need.

### Example

Say `byosnap-payments` is already running on your dev Snapend `abc123`. Today
you add a Stripe key to the Secrets Manager and you want your service to mount
it.

**What people try (and why it doesn't work):**

1. Open `snapser-byosnap-profile.json` and add `stripe-api-key @ dev-2026-08` to
   the `dev_template` secrets list.
2. Run `snapctl byosnap publish --byosnap-id byosnap-payments --version v0.2.0 ...`.
   This *does* update the stored template — so far so good.
3. Roll it out:
   `snapctl snapend update --snapend-id abc123 --byosnaps byosnap-payments:v0.2.0`.
4. Shell into the pod, look in `/opt/byosnap-secrets/` — **it's empty.**

Nothing is broken. `abc123` took its copy of the configuration back when
`byosnap-payments` was first added to it. Step 3 swapped the container image; it
did not re-read the template. The Snapend's manifest still says "no secrets", and
the manifest is what gets deployed.

Here's the part that makes this genuinely confusing: if you had instead spun up a
**new** Snapend and added `byosnap-payments` to it, the secret *would* be there —
because that's a first attach, so the template gets copied in. Same publish, two
different outcomes.

**What to do instead:**

- **For a Snapend that already runs this BYOSnap** → **Snapend → Customize
  Snapend**, find `byosnap-payments`, add the secret, deploy. You have to do this
  once per existing Snapend; there is no bulk path.
- **For Snapends that don't have it yet** → nothing extra to do. Publishing your
  updated profile (or editing the stored template via **BYOSnaps → \<your snap\>
  → Update**) already covers them. They'll pick it up when the BYOSnap is added.

<Note>
  This also means "add the BYOSnap to an existing Snapend for the first time" behaves
  like a brand-new Snapend, not like an update. If a Snapend has never had this
  BYOSnap before, attaching it now pulls the current stored template — secrets and all.
</Note>

### Where to make changes

| I want to change… | For… | Go to |
| ----------------- | ---- | ----- |
| CPU, memory, replicas, HPA, env vars, cmd, args, secrets | A Snapend that already runs this BYOSnap | **Snapend → Customize Snapend**, then deploy |
| The same | The production Snapend | **Promote to Prod → Customize BYOSnaps** |
| The same | Any Snapend that doesn't have this BYOSnap yet | Edit your profile + `snapctl byosnap publish`, or **BYOSnaps → \<your snap\> → Update** |
| The same | A Snapend, from CI or a script | `snapctl snapend download` → edit the manifest → `snapctl snapend apply` |
| Name, description, language | The BYOSnap itself | Your profile + `snapctl byosnap publish`, or **BYOSnaps → \<your snap\> → Update** |
| Which image version is running | One Snapend | `snapctl snapend update --snapend-id $id --byosnaps byosnap-x:v0.2.0` |

<Note>
  To confirm what actually landed, open **Snapend → Infrastructure → Dashboard**.
  It reads straight from the live Snapend manifest and shows each BYOSnap's CPU,
  memory, HPA state, and the counts of attached secrets, args and env vars. If
  it isn't there, it isn't deployed — regardless of what your profile file says.
</Note>

### Version control

Commit your `snapser-byosnap-profile.json` — it is the source of your BYOSnap's
template, and every publish pushes it.
Keeping it accurate and committed means each new Snapend — and each new attach of
this BYOSnap onto an existing Snapend — starts from the configuration you
actually intended. Just don't expect it to reconfigure Snapends that are already
running your snap.

### Direct Deploy
During development, you want to quickly test code changes without polluting your version history. The new Direct Deploy workflow streamlines this process:

1. **Develop**: Make code changes locally

Direct Deploy allows you to rapidly iterate without the overhead of version management, keeping your version history clean and focused on actual releases.

### Logs

Snapser recommends game studios to use the following best practices for logging in their BYOSnap.:

1. Logs should be in a structured JSON format.
2. If the JSON log has a field called **level** with one of the four values **debug, info, warn, error**,
   Snapser will automatically parse the log and show it in the correct color in the Snapser Logs tool.
3. If you have a field called **timestamp** in your JSON log, Snapser will use that as the
   timestamp for the log. The timestamp should be in the format **ISO-8601**.
4. Emit the request id from the `X-Request-Id` header as a **request-id** JSON field so Snapser
   can correlate all log lines of one request. See the
   [Logging & Request Correlation guide](/docs/custom/bring-your-own-snap/byosnap-logging) for
   code examples.

### 5. Snapser Sync & Promotion Tech

Snapser provides a way to sync Snapends with other Snapends and promote Snapends from one environment to another.
For BYOSnaps to tap into this system, every Snap exports their own settings. The destination
Snapend will then import these settings. In order to know, if the import would even work,
the destination Snapend will validate the import. All this is orchestrated by Snapser for you, and
all you have to do is implement the following endpoints.

#### Import Export Endpoints

1. **Export**: GET **/$prefix/$byosnapId/settings/export** - The endpoint should export the settings powering this BYOSnap in the format you see below.
2. **Import**: POST **/$prefix/$byosnapId/settings/import** - The endpoint should accept a payload in the format you see below and save the settings.
3. **Validate Import**: POST **/$prefix/$byosnapId/settings/validate-import** - The endpoint should accept a payload similar to the import and respond with a 200 if the BYOSnap is able to accept those settings.


```python
        'version': os.environ['BYOSNAP_VERSION'],
        'exported_at': int(time.time()),
        'data': {
            'character_settings': {}
        }
    }
    configuration = snapser.Configuration(
        host=os.environ['SNAPEND_STORAGE_HTTP_URL']
    )
    with snapser.ApiClient(configuration=configuration) as api_client:
        # Create an instance of the API class
        api_instance = snapser.StorageServiceApi(api_client)
        try:  # Storage Settings
            api_response = api_instance.storage_internal_get_blob(
                access_type='private',
                blob_key='character_settings',
                owner_id='byosnap_characters',
                gateway=os.environ['SNAPEND_INTERNAL_HEADER']
            )
            if api_response is None:
                return make_response(jsonify(response), 200)
            # Load storage data
            response['data']['character_settings'] = json.loads(
                api_response.value)
            return make_response(jsonify(response), 200)
        except ApiException as e:
            pass
    return make_response(jsonify(response), 200)
```

## Custom Events

BYOSnaps can register custom events using **RegisterByoEventTypes()** and publish events of those types using **PublishByoEvent()**.
In the EventBus Snap configuration registered event-types can be turned on for Webhooks and the WebSocket enabling events of those
to be received.

### Registering Event-Types

During startup of your BYOSnap call **RegisterByoEventTypes()** to register custom event-types. This is a create-or-replace operation
and is safe to call each time your BYOSnap starts.

**Payload and Identifying Event-Types**

Either the **Subject** or **EventTypeId** can be used to identify the payload. **Subject** is a fully qualified string for the event-type and
unique across all services. If you use **EventTypeId** to identify the payload, you'll want to use it in combination with **ServiceName**
(which is your BYOSnap ID).

For more information including example code see the
[Registering Event-Types](/docs/infra/snaps/eventbus#registering-event-types) section of
the [EventBus Snap](/docs/infra/snaps/eventbus) documentation.

### Publishing Events

Once you have registered your event-types, you can publish events of those types using **PublishByoEvent()**. See the example below.

For more information including example code see the [Publishing Events](/docs/infra/snaps/eventbus#publishing-events) section of
the [EventBus Snap](/docs/infra/snaps/eventbus) documentation.

## SDK

If you have a swagger.json file v3.x, at the root of your code or in the folder that you pass via **--resources-path** variable, Snapser will include your BYOSnap in the generated Snapend SDK. This means that your developers can start using your custom code without having to write any client side bindings.

<Note>
  You should check out the [BYOSnap Basic
  tutorial](/docs/guides/tutorials/byosnap-basic) to understand how you can
  automatically generate the swagger based on code annotations.
</Note>

Once you have the swagger.json ready and tagged with the appropirate custom tag **x-snapser-auth-types: user|api-key|internal** Snapser will generate all the SDKs for your BYOSnap:

1. User SDK - For game or app clients to use.
2. Api-Key SDK - For use from trusted server code.
3. Internal SDK - For other BYOSnaps to communicate with other snaps.

<Warning>
  Note: The Snapser SDK currently has a known limitation regarding 2XX
  responses. While your Swagger/OpenAPI spec may define specific schemas for
  responses like 201, 202, etc., the Snapser SDK will always default to using
  the schema defined for 200 as the response type for all 2XX responses. This is
  a constraint of the current SDK generation process.
</Warning>

## FAQs

#### Is the BYOSnap truly in my cluster?

Yes, unlike some other products out there that make you host your custom code in a separate cloud functions like environment,
Snapser BYOSnap is truly in your cluster. This means the latency for your custom code to talk to other Snaps is super low.

![BYOSnap Architecture](/images/docs/byosnap-architecture.png)

#### I am unable to reach my BYOSNap via an API call

Please check the BYOSnap Networking section. If you continue seeing issues, please reach out to your Snapser support team.

#### I am unable to reach my BYOSNap via the API Explorer but Curl works

This is most likely due to CORS. Your BYOSnap code needs enable CORS on the endpoints you have exposed. Most modern frameworks have a way to enable CORS using some sort of a library. Please reach out to us if you need help with this.

#### Is there any limit on the number of BYOSnaps?

Nope, there is no limit to the number of BYOSnaps you can add to your Snapend.
