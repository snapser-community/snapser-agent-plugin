# Custom User Manager Tool
Snapser allows you to bring in your custom HTML/CSS/JS code as a User Manager tool powered by your BYOSnap. User Manager tool allows you to expose and update user specific data from your BYOSnap.

## Concept
A BYOSnap user manager tool is a HTML/JS/CSS based tool that is used to view and manipulate user data. You can upload these tools to Snapser as part of the BYOSnap publish process. Once uploaded, the tool will be available under your Snapser User Manager tool.

The Snapser Web app renders this tool in an iframe and injects the Snapser JS SDK into the tool. This allows you to use the Snapser JS SDK to make network calls to your BYOSnap using simple JavaScript functions.

## Building the Tool
You can build the configuration tool using any HTML/CSS/JS framework of your choice. Since the Snapser JS Tool SDK is injected into the tool at runtime, you can use it to make network calls to your BYOSnap. Below is an example of a simple configuration tool built using plain HTML/JS.

```html
<!doctype html>
<meta charset="utf-8" />
<meta name="viewport" content="width=device-width,initial-scale=1" />
<title>BYOSnap User Tool</title>

<style>
  :root {
    --bg: white;
    --text: black;
    --input-bg: white;
    --input-text: black;
    --input-border: #ccc;
  }

  body {
    font: 14px system-ui;
    margin: 16px;
    background-color: var(--bg);
    color: var(--text);
  }

  input,
  button {
    padding: 8px;
    background-color: var(--input-bg);
    color: var(--input-text);
    border: 1px solid var(--input-border);
  }

  .row {
    display: flex;
    gap: 8px;
  }
</style>

<h1>BYOSnap User Tool</h1>
<form id="f">
  <div class="row">
    <input id="user" name="User" placeholder="Type something…" />
    <input id="txt" name="Characters" placeholder="Type something…" />
    <button type="submit">Save</button>
  </div>
  <div id="msg" role="status" aria-live="polite"></div>
</form>

<script>
  (async function () {
    await window.Snapser.ready();

    const f    = document.getElementById('f');
    const user = document.getElementById('user');
    const txt  = document.getElementById('txt');
    const msg  = document.getElementById('msg');

    // ---------- THEME HANDLING ----------

    function applyTheme(mode) {
      const m = mode === 'dark' ? 'dark' : 'light'; // normalize

      if (m === 'dark') {
        document.documentElement.style.setProperty('--bg', '#1b2225');
        document.documentElement.style.setProperty('--text', '#ffffff');
        document.documentElement.style.setProperty('--input-bg', '#1e1e1e');
        document.documentElement.style.setProperty('--input-text', '#ffffff');
        document.documentElement.style.setProperty('--input-border', '#444444');
      } else {
        document.documentElement.style.setProperty('--bg', '#ffffff');
        document.documentElement.style.setProperty('--text', '#000000');
        document.documentElement.style.setProperty('--input-bg', '#ffffff');
        document.documentElement.style.setProperty('--input-text', '#000000');
        document.documentElement.style.setProperty('--input-border', '#cccccc');
      }
    }

    // Initial theme from SDK (set via host.welcome or default)
    console.log('Initial theme from Snapser._theme:', window.Snapser._theme);
    applyTheme(window.Snapser._theme);

    // Subscribe to future theme updates (host.theme.update)
    window.Snapser.onTheme((mode) => {
      console.log('Received theme update from Snapser:', mode);
      applyTheme(mode);
    });

    // ---------- END THEME HANDLING ----------

    // Load user data
    try {
      const { id } = await window.Snapser.user.getId();
      if (id) user.value = id;

      const { data } = await window.Snapser.user.rpc('/custom', {
        method: 'GET',
      });
      if (data?.payload) txt.value = data.payload;
    } catch (_) {}

    // Save data — all_pods: true sends the request to every pod in the cluster
    f.addEventListener('submit', async (ev) => {
      ev.preventDefault();
      msg.textContent = 'Saving…';
      try {
        await window.Snapser.user.rpc('/custom', {
          method: 'POST',
          body: { payload: txt.value },
          all_pods: true,
        });
        msg.textContent = 'Saved ✅';
      } catch (e) {
        msg.textContent = 'Failed ❌';
      }
    });
  })();
</script>
```

There are a few things to note in the above example:
1. You do not need to include the Snapser JS SDK script tag in your HTML. The Snapser platform will automatically inject the SDK into your tool at runtime.
1. You use the `window.Snapser.ready()` method to initialize the SDK and wait for it to be ready.
1. You can use the `window.Snapser.user.getId` method to get the user ID of the user that is currently loaded in the User Manager tool.
1. You can use the `window.Snapser.user.rpc` method to make network calls to your BYOSnap. This method takes two arguments:
   - The first argument is the endpoint you want to call. This endpoint maps to your BYOSnap endpoint `/v1/$byosnapId/settings/users/<user_id>/<your-endpoint>`.
   - The second argument is an options object that contains the HTTP method, headers, and body of the request.
1. The `window.Snapser.user.rpc` method returns a promise that resolves to the response from your BYOSnap.

### Broadcasting to All Pods

By default, `user.rpc` sends the request to a single pod. If you set `all_pods: true` in the options, the request is broadcast to **every pod** running your BYOSnap in the cluster.

```js
await window.Snapser.user.rpc('/custom', {
  method: 'POST',
  body: { payload: txt.value },
  all_pods: true,
});
```

This is useful when your BYOSnap holds in-memory state that needs to be refreshed across all instances without a restart.

#### When to use `all_pods: true`

| Scenario | Why |
| --- | --- |
| **Reloading Remote Config** — Your BYOSnap caches remote config values in memory at startup. An admin updates a value and every pod needs to re-fetch immediately. | Without the broadcast each pod keeps serving stale config until it restarts or its polling interval fires. |
| **Flushing an in-memory cache** — Your BYOSnap maintains a local LRU cache of player profiles or asset manifests for performance. An admin purges a corrupt entry. | Only the pod that handles the request would flush; other pods continue serving the bad data. |
| **Toggling a feature flag at runtime** — Your BYOSnap reads feature flags into memory on boot. A game-ops engineer enables a new event mode live. | Players connected to different pods would see different feature states until all pods restart. |
| **Broadcasting a maintenance or shutdown signal** — You want every pod to start draining connections or entering read-only mode before a deploy. | A single-pod request would only drain one instance; the rest keep accepting new work. |

#### When you do NOT need `all_pods`

| Scenario | Why |
| --- | --- |
| **Writing to a database or shared store** — Your BYOSnap persists config to Postgres, Redis, DynamoDB, or Snapser Storage and reads it on every request. | All pods already read from the same source of truth; updating it once is enough. |
| **Updating a single player's data** — An admin edits one user's inventory or profile through the User Manager tool. | Player data lives in a shared store; only one write is needed. |
| **Queueing an async job** — Your config tool triggers a background task (e.g. send a push notification campaign) that a worker picks up from a queue. | The job goes onto a shared queue; broadcasting it would create duplicate work. |
| **Logging or auditing an admin action** — Your BYOSnap writes an audit entry when a setting changes. | One audit row per action is correct; broadcasting would create duplicate audit logs. |

<Note>
  When `all_pods` is not set, or is set to `false`, the request is routed to a single pod via normal load balancing. This is the default and the right choice for most write-to-store operations.
</Note>

## Publishing the Tool
Once you have built your configuration tool, you can publish it to Snapser as part of your BYOSnap. You can do this by including the HTML file in the `snapser-resources` folder of your BYOSnap project. The tool should be named with a prefix `snapser-user-tool-` followed by your desired name and end with `.html` For example: `snapser-user-tool-characters-custom.html`. Here is a real example of uploading a configuration tool as part of the BYOSnap publish process:

```bash
ajinkyas-mbp:byosnap-python Ajinkya$ snapctl byosnap publish --byosnap-id byosnap-advanced --version "v0.0.1" --path . --resources-path ./snapser-resources/.
```

When you publish your BYOSnap, Snapser will upload the user tool and make it available under the User Manager tool.

<Note>
  You can upload upto 50 user tools per BYOSnap. Just name them with the `snapser-user-tool-` prefix and they will be automatically detected by `snapctl`.
</Note>

## Accessing the Tool
Once your BYOSnap is published and you add the latest BYOSnap to your Snapend, you can access your custom user tool by visiting the `User Manager` tool under Quick links and searching for a user. You will see your custom tool listed under your BYOSnap name.
