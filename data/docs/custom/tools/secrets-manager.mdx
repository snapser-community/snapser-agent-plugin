# Secrets Manager

## Concept

The Secrets Manager is where you store the credentials, API keys, certificates
and other sensitive blobs your BYOSnaps need to read at runtime. Each secret
is a small piece of text — anything you can paste into a text box or upload
as a file — that Snapser stores encrypted and mounts into your BYOSnap
container at startup.

Secrets are **exclusively a BYOSnap feature**. They are not consumed by
Snapser-managed services, and there is no API that exposes their values
to anything other than the BYOSnap pods that reference them. Inside the
container they appear as files at a fixed mount path, one file per secret:

```text
/opt/byosnap-secrets/$file_name
```

The contents of each file is the raw value you stored, as a UTF-8 string.
Your code reads it with whatever file API the language gives you.

### The (file_name, tag) model

Every secret in the Secrets Manager is identified by a pair: a **file name**
and a **tag**.

- **file name** — the user-facing name for the secret. This is also what
  the mount path uses (`/opt/byosnap-secrets/$file_name`). Pick names
  that read like file names from your project — for example
  `service-account.json`, `aws-iam.pem`, `stripe-api-key`.
- **tag** — a user-supplied label that picks a specific revision of that
  file. Tags are strings _you_ choose at create time. Common conventions
  are versions (`v1.2.3`), date stamps (`prod-2024-01`) or release names
  (`stable`). The Secrets Manager does not invent or auto-increment tags
  — they are exactly the strings you supply.

A BYOSnap pins a reference to a concrete `(file_name, tag)` pair. There is
no `latest` sentinel and no implicit "most recent" resolution at deploy time
— what you pick is what mounts. The picker auto-fills the tag dropdown with
the most recently created tag as a convenience, but you can override it.

Where that reference is *stored* matters. For anything already deployed, the
reference lives in the **Snapend manifest** — a copy taken from the BYOSnap's
template when the snap was added to that Snapend. Editing the template later
does not update that copy. See
[Referencing a secret from a BYOSnap](#referencing-a-secret-from-a-byosnap)
below — this is the number one source of "why isn't my secret mounting?".

### Immutability

Secrets are **immutable once created**. There is no edit verb. If you need
to change a value, the workflow is:

1. Create a new tag under the same file name with the new value.
2. Repoint every BYOSnap that references the secret at the new tag, using
   **Customize Snapend** on each Snapend that already runs it. (Re-publishing an
   edited profile only covers Snapends that add the snap later — see
   [Referencing a secret from a BYOSnap](#referencing-a-secret-from-a-byosnap).)
3. Once nothing references the old tag, delete it.

This guarantees that a tag a BYOSnap pinned to never silently changes
underneath it. Rotations are explicit and reviewable in the diff.

<Note>
  Tags are unique per file name. Re-using a tag that already exists under a file
  name returns a `409 Conflict`. Pick a new tag string for each rotation.
</Note>

## Pre-requisites

You need at least a viewer role for the scope you're working in
(`company-view`, `game-view` or `cluster-view`) to open the Secrets Manager
in read-only mode.

To create or delete secrets you need one of the following roles in the
scope you're working in:

- `company-admin`, `game-admin` or `cluster-admin`
- `company-edit`, `game-edit` or `cluster-edit`

Users without write access still see the page but in a read-only view with
a banner explaining the restriction. Revealing a value requires the same
permissions as create/delete.

## Tool Location

The Secrets Manager lives under **BYOSnaps** in the left nav and is
available at three scopes. All three render the same UI against the same
per-application secret pool — the scope only changes which permissions
gate the page and which URL is used to back the calls.

| Scope           | Where to find it             | What you see                                                                                 |
| --------------- | ---------------------------- | -------------------------------------------------------------------------------------------- |
| **Company**     | Studio → BYOSnaps → Secrets  | Pick an application from the top-right picker first, then manage that application's secrets. |
| **Application** | App → BYOSnaps → Secrets     | Manages the current application's secrets directly.                                          |
| **Snapend**     | Snapend → BYOSnaps → Secrets | Manages secrets for the application that owns this snapend.                                  |

![Secrets Manager](/images/docs/secrets-manager-overview.png)

Once you're on the page, **+ Secret** in the top-right opens the inline
create form between the page header and the table.

<Note>
  At company scope the manager waits until you pick an application before
  showing the table. Secrets are inherently per-application on the backend —
  there is no company-wide secret pool — so the picker tells the manager which
  application to read from.
</Note>

## Creating a secret

Click **+ Secret**. The inline form drops in between the header and the
table. Three fields, all required:

1. **File name** — the user-facing identity of the secret and the basename
   it will mount as. Letters, numbers, `-`, `_` and `.` only. Max 253
   characters. The form shows the full mount path next to the input so
   you can see exactly where it will land:
   `/opt/byosnap-secrets/$file_name`.
2. **Tag** — your chosen revision label. Same character set as file name,
   max 64 characters. Must be unique within this file name.
3. **Value** — the contents of the secret. Two input modes:
   - **Paste value** — type or paste the value into the textarea.
   - **Upload file** — pick a file from your computer. Snapser reads it
     as UTF-8 text and sends the contents as a string. The file name
     field auto-fills from the file you picked if you haven't typed
     anything there yet.

Hit **Save**. The new entry appears in the table and the form closes.

![Add Secret](/images/docs/secrets-manager-add.png)

### Limits

| Field                       | Limit                                              |
| --------------------------- | -------------------------------------------------- |
| File name length            | 253 characters                                     |
| File name pattern           | `^[-._a-zA-Z0-9]+$`                                |
| Tag length                  | 64 characters                                      |
| Tag pattern                 | `^[-._a-zA-Z0-9]+$`                                |
| Value size                  | 65,536 bytes (64 KiB)                              |
| Tags per file name          | No fixed cap — keep what's in use, delete the rest |
| Secrets per BYOSnap profile | 5 per environment template (dev / stage / prod)    |

The form enforces all of these client-side; the backend rejects anything
that slips through.

## Tags table

Each row in the main table is one **file name**. Click the chevron at the
left of a row to expand its **tags table**, which lists every tag under
that file name, newest first.

![Expanded Tags](/images/docs/secrets-manager-expanded.png)

| Column        | What it shows                                                                                                                                                        |
| ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Tag**       | The tag string you supplied at create time.                                                                                                                          |
| **Created**   | Local timestamp of when the tag was created.                                                                                                                         |
| **Usage**     | One chip per snapend that references this tag, with the BYOSnap names in a tooltip. Empty cell means nothing currently references this tag, so it is safe to delete. |
| **(actions)** | **Reveal** and **Delete** — see below.                                                                                                                               |

### Revealing a value

Click **Reveal** on any tag row. Snapser issues a per-tag reveal call and
shows the plaintext in a modal. The modal auto-closes after one minute as
a guardrail against an open laptop on a desk. There is a **Copy** action
inside the modal for grabbing the value into your clipboard.

<Note>
  Reveal is the only path that exposes plaintext anywhere in the portal. The
  list and detail responses always return a `********` placeholder for the value
  field. Each Reveal is a discrete call — there is no bulk reveal — and the
  action is gated by the same `*-edit` / `*-admin` roles as create and delete.
</Note>

### Deleting a tag vs deleting a file

Two delete actions are exposed:

- **Delete tag** (inside the expanded tags table) — removes a single
  revision under a file name. The action is rejected by the backend if
  any snapend's BYOSnap currently references this tag — the Usage column
  shows you exactly what is in the way. Delete the references first
  (or repoint them at another tag) and try again.
- **Delete file** (on the summary row) — removes the file name and every
  tag underneath it. Also rejected if any tag is referenced.

In both cases the portal surfaces the backend's rejection message in a
toaster so you can see which references are blocking the delete.

## Rotation recipe

Because secrets are immutable, rotation is a small dance:

1. **Create a new tag** under the same file name with the new value.
2. **Repoint every reference** to the old tag. The Usage column on the old
   tag names each snapend and BYOSnap that needs editing — work that list.
   For each one, go to **Snapend → Customize Snapend**, select the BYOSnap,
   and switch the tag. Re-publishing an edited profile will **not** do this for
   you; it only changes what future attaches of the BYOSnap start from. Do
   update the template too — via your profile or **BYOSnaps → \<your snap\> →
   Update** — so new Snapends don't start out on the retired tag.
3. **Deploy** the snapend so the new mount lands in the running pods.
4. **Delete the old tag** once the Usage column is empty.

This deliberately keeps the old tag around until you've moved every
consumer — a pinned reference never breaks underneath you, and the diff
in Promote-to-Prod shows the rotation as a single explicit change.

## Referencing a secret from a BYOSnap

Creating a secret does nothing on its own. A BYOSnap only mounts a secret
once something references it — and **where** you add that reference decides
whether it affects a Snapend you already have, or only ones you make later.

The same picker component shows up in five places, but they fall into two very
different groups. This is the part that trips people up:

| Where | What it edits | Reaches a Snapend that already runs this BYOSnap? |
| ----- | ------------- | -------------------------------------------------- |
| **Snapend → Customize Snapend** | That one Snapend's manifest | **Yes** — this is the one that changes what's running |
| **Promote to Prod → Customize** | The production Snapend, at promote time | **Yes**, on the production cut |
| **BYOSnap → Update** | The BYOSnap's stored template | **No** — applies when the snap is *next added* to a Snapend |
| **BYOSnap → Add** | The stored template, at publish time | **No** — same as above |
| **BYOSnap Profile Tool** | Your `snapser-byosnap-profile.json` on disk | **No** — feeds the stored template on your next publish |

The top two edit a **deployment profile** — one BYOSnap's live block inside one
Snapend's manifest. The bottom three edit the **BYOSnap profile**, which is a
template a Snapend only reads at the moment the BYOSnap is added to it.

<Warning>
  **Adding a secret to your profile and re-publishing will not give the secret to a
  Snapend that already runs this BYOSnap** — not even if you then bump that Snapend
  to the new version. A version bump swaps the container image; it does not re-read
  the template. Use **Customize Snapend** for those. Snapends that add the BYOSnap
  *after* your publish will pick the secret up automatically. See
  [Profile vs. Snapend Manifest](/docs/custom/bring-your-own-snap#profile-vs-snapend-manifest).
</Warning>

### How it works

Think of the template as a rubber stamp, and each Snapend as a page.

Publishing an updated profile — or editing via **BYOSnap → Update** — re-carves
the stamp. Every page you stamp **from now on** gets the new design. Pages you
already stamped are unchanged; they're in a drawer with the old design on them.

**Customize Snapend** is you picking up one already-stamped page and writing on
it directly. That page changes immediately. The stamp doesn't.

So if three dev Snapends already run your BYOSnap and you re-carve the stamp, all
three still have the old secrets — you have to edit each one. But the next Snapend
you stamp gets it right for free. Same edit, two different outcomes, depending
entirely on whether the page was already stamped.

The upside of writing on the page directly is that rotating a secret costs you
nothing but a deploy: no new BYOSnap version, no rebuild, no repo change. See
[Why they're separate](/docs/custom/bring-your-own-snap#why-theyre-separate).

### Per-environment lists are independent

Each environment tab (`dev_template`, `stage_template`, `prod_template`)
carries its own list of secret references. A dev profile can mount
`service-account.json @ dev-2024-01` while prod mounts
`service-account.json @ prod-2024-01`. Adding a secret on the dev tab
does not put it on the stage or prod tab — you have to add it on each tab you
want it on.

### Using the picker

Click **+ Add secret**. A row appears with two dropdowns side by side:

1. **File name** — autocomplete of every secret in this application.
   Picks already used by another row are disabled so you can't reference
   the same file twice in one profile.
2. **Tag** — once you pick a file name, the tag dropdown lists every tag
   that exists under it and auto-fills with the most recently created
   tag as a convenience. You can change it to any other concrete tag.

You can add up to **5 secrets per environment tab**. The picker disables
**+ Add secret** once you hit that ceiling.

The form refuses to save if a row is partially filled — either pick a
file name + tag or remove the row with the trash icon. The picker flags
incomplete rows in red and the parent form shows a toaster with the
offending tab name when you hit Save.

<Note>
  If a referenced secret has since been deleted from the Secrets Manager, the
  picker shows a warning triangle and a tooltip on that row. The save will fail
  until you either remove the row or recreate the secret with the same file name
  and tag.
</Note>

## Reading secrets in your container

At BYOSnap startup, Snapser mounts every referenced secret as a file under
`/opt/byosnap-secrets/`. The file name is exactly the `file_name` you
chose; the contents are the raw value of the tag your profile pinned.

```text
/opt/byosnap-secrets/service-account.json
/opt/byosnap-secrets/stripe-api-key
/opt/byosnap-secrets/aws-iam.pem
```

Read them with whatever file API your language gives you:

<CodeGroup title="Reading a secret">

```python {{ title: 'Python' }}
from pathlib import Path

# The contents are the raw value as a UTF-8 string.
service_account = Path('/opt/byosnap-secrets/service-account.json').read_text()

# JSON-shaped secret? Parse it normally.
import json
creds = json.loads(service_account)
```

```javascript {{ title: 'Node' }}
const fs = require('fs')

// Sync read at startup is fine — the file is already on disk when your
// process boots.
const serviceAccount = fs.readFileSync(
  '/opt/byosnap-secrets/service-account.json',
  'utf8'
)

const creds = JSON.parse(serviceAccount)
```

```go {{ title: 'Go' }}
package main

import (
	"encoding/json"
	"os"
)

func loadCreds() (map[string]any, error) {
	data, err := os.ReadFile("/opt/byosnap-secrets/service-account.json")
	if err != nil {
		return nil, err
	}
	var creds map[string]any
	if err := json.Unmarshal(data, &creds); err != nil {
		return nil, err
	}
	return creds, nil
}
```

</CodeGroup>

<Note>
  Snapser writes secrets to disk before your process starts, so a synchronous
  read at boot is safe. The pod is restarted whenever the pinned tag changes
  (i.e. when you deploy a profile that references a different tag), so you can
  cache the value in memory for the life of the process.
</Note>

### What about environment variables?

Snapser does **not** expose secrets through environment variables. Two
reasons:

1. Env vars are visible to anything that can read `/proc/$pid/environ`,
   including some debug tools that don't expect to leak secrets.
2. Many credentials (JSON service accounts, PEM-encoded keys) have line
   breaks and special characters that don't survive env-var round-trips
   cleanly.

If your library or framework expects a file path, point it at
`/opt/byosnap-secrets/$file_name`. If it expects a string, read the
file at startup and pass the contents.

## BYOSnap details view

The BYOSnap details page (Snapend → BYOSnaps → click a snap) has a
**Secrets** row in the Configuration card showing every secret reference
attached to the currently selected env template, as `file_name @ tag`
chips. Chips for references whose file name no longer exists in the
Secrets Manager get a warning treatment with an explanatory tooltip — a
quick visual cue that a referenced secret has been deleted and needs
attention before the next deploy.

The details view never reveals values — it is purely the configuration
view. Use the Secrets Manager's Reveal action if you need to inspect a
plaintext value.

The Snapend Infra Dashboard (**Snapend → Infrastructure → Dashboard**)
also surfaces a per-BYOSnap **Secrets** count alongside CPU, memory,
the real autoscaler (HPA) state, args and env vars — click the count
to pop the same `file_name @ tag` list. Handy as an at-a-glance
verification that what you wired up in the Customize-Snapend flow
actually deployed.

## FAQs

### I added a secret to my BYOSnap profile and re-published. Why doesn't my Snapend have it?

Your publish did update the BYOSnap's stored template. The problem is that a
Snapend only reads that template **once** — at the moment the BYOSnap is added to
it. Your Snapend took its copy back when you first added the snap, and it has
owned its own configuration ever since.

To get the secret mounted on that Snapend, go to **Snapend → Customize Snapend**,
add the secret to the BYOSnap, and deploy. Repeat for each Snapend that already
runs it.

Snapends that add this BYOSnap *after* your publish need nothing extra — they'll
pick the secret up on attach.

Full explanation in
[Profile vs. Snapend Manifest](/docs/custom/bring-your-own-snap#profile-vs-snapend-manifest).

### I bumped my Snapend to the new BYOSnap version. Why still no secret?

Because a version bump rolls out a new container **image**, not a new
configuration. `snapctl snapend update --byosnaps byosnap-x:v0.2.0` changes which
build is running and leaves the Snapend's manifest — CPU, env vars, secrets and
all — exactly as it was.

Configuration changes on an attached BYOSnap only come from **Customize Snapend**
or a manifest edit.

### I updated the BYOSnap's template. Why didn't my existing Snapends change?

By design. Editing the stored template — through your profile or **BYOSnap →
Update** — sets what the *next* attach starts from. It never reaches back into
Snapends that already run the snap; otherwise editing a template could silently
re-configure production.

Every Snapend already running this BYOSnap needs its own **Customize Snapend**
pass. The Usage column in the tags table tells you which Snapends reference a
given tag, which is a good checklist to work from.

### Does adding the BYOSnap to an old Snapend count as a fresh start?

Yes. "First attach" is per BYOSnap **per Snapend**, not per Snapend. If a
six-month-old Snapend has never had this BYOSnap before, adding it now pulls the
current stored template — secrets included. It behaves exactly like a brand-new
Snapend would.

### How do I tell what a Snapend is actually mounting right now?

**Snapend → Infrastructure → Dashboard**. It reads from the live Snapend
manifest and shows a Secrets count per BYOSnap — click it for the
`file_name @ tag` list. The BYOSnap details page (**Snapend → BYOSnaps →**
click a snap) shows the same list in its Configuration card. From the CLI,
`snapctl snapend download --snapend-id $id --category snapend-manifest
--format json --out-path .` gives you the whole manifest.

If the secret isn't in one of those, it isn't deployed — no matter what your
profile file says.

### Why are secrets immutable?

So a BYOSnap that pinned `service-account.json @ prod-2024-01` keeps
mounting that exact value forever, until the profile is explicitly
updated to point somewhere else. Rotations are deliberate and reviewable
in the Promote-to-Prod diff rather than ambient changes that ship the
next time a pod restarts.

### How do I rotate a secret?

Create a new tag under the same file name, repoint your BYOSnap profile
at the new tag, deploy, then delete the old tag. See
**Rotation recipe** above for the full walkthrough.

### What does the warning chip on the BYOSnap details page mean?

It means the BYOSnap is pinned to a secret whose `file_name` no longer
exists in the Secrets Manager — usually because someone deleted it. The
next deploy of this snapend will fail validation. Either recreate the
secret under the same file name and tag, or edit the BYOSnap profile to
remove the reference.

### Can I share a secret across multiple applications?

No. Secrets live inside an application and are not visible across
applications. If two applications need the same credential, create it
in both Secrets Managers.

### Can I share a secret across environments inside one application?

Yes — there is one secret pool per application, and any environment's
configuration can reference any `(file_name, tag)` in it. In
practice teams keep separate tags per environment (`dev-2024-01`,
`stage-2024-01`, `prod-2024-01`) so a rotation in one environment does
not change another.

### Can a single BYOSnap mount the same secret twice?

No. The picker disables a file name in the dropdown once another row in
the same profile is using it. Mounting the same file twice doesn't add
anything — the file would end up at the same path either way.

### What's the cap on tags per file name?

There isn't a fixed cap. The recommended practice is to delete tags once
they are no longer referenced (the Usage column tells you which are
safe). Long-lived rotations should not accumulate dozens of tags.

### Can I see who created or deleted a secret?

Yes — the Audit log records create and delete actions on secrets along
with the user who performed them. Reveal actions are also audited.

### Why aren't secrets injected as environment variables?

Env vars leak through `/proc/$pid/environ` and don't round-trip
multi-line or binary-ish credentials cleanly. The file-mount model
avoids both problems. See **What about environment variables?** above.

### What happens if I try to delete a tag that's in use?

The backend rejects the delete with a message naming the snapend and
BYOSnap that still references the tag. The Usage column in the tags
table shows you the same information up front, so you can move the
references first.
