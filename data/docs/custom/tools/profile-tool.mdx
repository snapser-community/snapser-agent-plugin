# Profile Tool
This tool allows you to generate, import, edit and export BYOSnap profiles for your custom snaps.

<Warning>
  **A profile sets a template, not live settings.** Publishing an edited profile
  updates your BYOSnap's stored template — but a Snapend only reads that template
  at the moment the BYOSnap is added to it. Editing a profile here and
  re-publishing will not change CPU, memory, replicas, env vars, HPA or secrets on
  a Snapend that already runs your snap; use **Customize Snapend** for those. See
  [Profile vs. Snapend Manifest](/docs/custom/bring-your-own-snap#profile-vs-snapend-manifest).
</Warning>

## Concept
Every developer building a BYOSnap wants to have a way to configure the snap's infrastructure settings. Snapser provides a way to do this by using a BYOSnap profile. This profile is a JSON or a YAML file that contains the following information:
- **Name**: The name of the BYOSnap
- **Description**: A brief description of the BYOSnap
- **Platform**: The platform the BYOSnap is built for. Options are 'linux/arm64' or 'linux/amd64'
- **Language**: The language the BYOSnap is built in. Options are 'go', 'node', 'python', 'java', 'csharp', 'cpp', 'rust', 'ruby', 'php', 'perl', 'clojure', 'lua', 'ts', 'js', 'kotlin', 'c'
- **Prefix**: The path prefix for the BYOSnap.
- **Ingress Ports**: External and Internal ingress ports exposed for the BYOSnap
- **Readiness Probe Configuration**: Initial delay seconds and path for the readiness probe.
- **Dev Template** - CPU, Memory, Min Replicas, Command, Args, Env Params for Development Snapends
- **Stage Template** - CPU, Memory, Min Replicas, Command, Args, Env Params for Staging Snapends
- **Prod Template** - CPU, Memory, Min Replicas, Command, Args, Env Params and an optional **HPA** block for Production Snapends. HPA (Horizontal Pod Autoscaler) lets you autoscale your BYOSnap between a min and max replica count based on CPU and memory thresholds. HPA is **production only**; on dev and stage the field must be `null`.

Each of the three environment templates can also carry up to five **Secrets** —
references into the [Secrets Manager](/docs/custom/tools/secrets-manager), each a
`(file_name, tag)` pair that Snapser mounts at `/opt/byosnap-secrets/$file_name`
inside the pod. The three lists are independent: adding a secret on the Dev tab
does not add it to Stage or Prod.

<Note>
  Secrets you set here reach a Snapend only when the BYOSnap is added to it. To add
  a secret to a Snapend that already runs the snap, use **Snapend → Customize
  Snapend** instead — publishing an updated profile will not do it.
</Note>

## Usage
Rather than making developers manually create this profile, Snapser provides a tool that allows developers to generate, import, edit and export BYOSnap profiles.

![BYOSnap Profile Tool](/images/docs/byosnap-profile-tool.png)

### Generate
Use the tool form to enter the details of your BYOSnap profile. Once you have entered all the details, click on the **Download** button to generate the profile. The profile will first be validated and then if it looks good, it will be downloaded as a `.yml` or a `.json` file, depending on your selection.

### Validate
If you have either imported or edited a profile, you can validate it using the **Validate** button.

## Download
Once you have generated or edited a profile, you can download it using the **Download** button.

### Import
If you have a profile saved in your BYOSnap code base. Now one of your developers manually updates it. You can import the updated profile using the **Choose File** viz. Import button. The profile will be validated and whichever attributes are valid will be added to the tool UI. Those that are invalid will not be populated in the tool. Instead you will get a message indicating the error.

If your profile is valid or once you have fixed any errors you got from the validation, you can save the profile using the **Download** button.

### Activity Log
The tool maintains the last 10 activities performed on the tool. This includes the time of the activity, and the result. This is useful for tracking changes made to the profile.

### Autoscaler (Production tab)
On the **Production** tab, the tool surfaces an **Autoscaler** subsection under **Scaling**. It is off by default — the **Replicas** field above governs and your snap runs with a static replica count. Flipping the toggle on enables HPA and unlocks the following fields:

- **Min Replicas** / **Max Replicas** — the bounds the autoscaler will respect. Min must be greater than 0 and less than or equal to Max.
- **CPU Utilization Threshold** — scale up when the average CPU across replicas exceeds this percentage (1–100).
- **Memory Utilization Threshold** — same, for memory (1–100).
- **Scale Up Behavior** — how aggressively to add pods. `Stabilization Window` is how long the controller waits before scaling up again (0–3600s). `Period` is the polling interval (0–300s). `Policy` is either a **Percent** of current replicas to add per period, or a fixed **Pods** count — exactly one is set at a time.
- **Scale Down Behavior** — same shape as Scale Up, but the `Percent` policy is capped to 1–99% (the autoscaler can't scale to zero in one step).

When HPA is on, the Static **Replicas** field above is disabled — the HPA Min/Max take over. The Dev and Stage tabs do not show the Autoscaler subsection at all; HPA is production-only.
