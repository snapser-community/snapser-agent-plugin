# Matchmaking

The Matchmaking snap makes it easy to match users together based on an
arbitrary set of rules. In addition to custom attributes, the service is also
fully integrated with the Leaderboards Snap, and Statistics snap to provide
a seamless experience for your users.

## Components

There are a few key concepts to understand when using the Matchmaking snap.

### Setup Matchmaking
This is where you can create Match Profiles and Rule Sets via the Matchmaking Configuration tool.
1. **Base Settings**: These are matchmaking settings like min and max players size, match acceptance rules, team formation rules and backfilling rules. These settings determine the behavior of the matchmaker.
2. **Allocation**: The Matchmaking snap has been integrated with the Snapser relay and game server fleet and lobbies snaps. You can decide if you want the match to be allocated to your relay, a specific game server fleet or a lobby.
3. **Rule**: A rule is a specific condition that must be met for tickets to be matched. There are several types of rules. For example, a rule can be a custom tag rule, a custom string or number rule, a statistic rule, a leaderboard rule or a latency rule. The matchmaking snap will pull in data from the statistics and leaderboard snaps to match users based on these rules.
4. **Rule set**: The rule set is a collection of rules that are used to match users together. A match profile can have multiple rule sets, and matches can be created for each rule set. All rules within a rule set are ANDed together.
5. **Match Profile**: The match profile holds all the information you see above that needed to match users together. Typically, there will be a different match profile for each game mode in your game.

### Use Matchmaking
This is where a game client will create tickets to match users together via the Matchmaking API.
1. **Ticket**: A ticket is a request to match a user. It may contain custom attributes or simply a user's id. When queuing for a match, it is expected that a single Ticket is created for each user/group. A game client can poll or use the Snapser Websocket to get updates on the status of their ticket.

#### Profile-Specific Queuing

When creating a ticket, you can optionally specify a `profile_name` to restrict that ticket to a specific Match Profile. This is useful when your game has multiple game modes and you want to ensure that a ticket is only evaluated against the rules of a particular mode.

- **Hinted tickets**: Tickets created with a `profile_name` are placed into a dedicated queue for that profile. They will only ever be matched within that profile's rules.
- **Unhinted tickets**: Tickets created without a `profile_name` are placed into a general queue and will be evaluated against all active Match Profiles.

There is no overlap between the two queues -- a ticket is either hinted or unhinted.

### Behavior

The Matchmaking loop runs continuously, always checking if there are enough tickets that meet the criteria defined in the Match Profiles to form a match.

At a high-level, the Matchmaking loop works as follows:

1. Fetch all configured Match Profiles.
2. For each Match Profile:
   a. Fetch all tickets that are eligible for matching based on the profile's queue settings and the ticket's age.
   b. Evaluate the tickets against the profile's rule sets to find groups of tickets that match together.
3. If there are enough tickets that match the rule set, create a match and assign the tickets to the match.
4. Repeat.

#### Automatic Ticket Cleanup on Disconnect

When [WebSockets](/docs/infra/snaps/hermes) are enabled on your snapend, the Matchmaking snap will automatically delete a user's ticket if the user disconnects from the WebSocket. This prevents stale tickets from occupying queue slots while the user is offline.

## Base Settings

Each Match Profile has a set of base settings that define the behavior of the matchmaker. These settings include

### Match Size
This setting controls the minimum and maximum number of players in a match. Eg: say your game has a 10v10 mode, then the min and max players would be 10.

### Match Acceptance
This setting tells the matchmaker, if a match should be created only if all players accept the match. If enabled, all players must accept the match before the timeout period. If not all players accept the match, the match will be cancelled.

### Team Formation

Sometimes, just putting the players into the same match is not enough. The Matchmaking Service also has the ability to create teams of the players in the match. Whether you're building a free-for-all, a 3v3 team battler, or a 16v16 large team battle, the Matchmaking Service can create your desired team for you automatically.

Team Formation Settings are configured in the Match Profile. You can specify the number of teams to split players across and minimally how many players needed per team to start a match.

By default, teams are randomly assigned to all players in the match. If queued as a party, the Matchmaking Service will attempt to keep all party members on the same team. If this is not important to your game, you may enable the setting `allow party separation` within the "Team Formation Settings" field.

You can also specify how teams are assigned via the Team Formation's 'Strategy' and 'Strategy Argument'. For example, if you have an `elo` statistic rule, you can choose to fill out teams in an alternating fashion based on the `elo` statistic value, ensuring they are competitively balanced. You can use any "number" based rule (statistics, leaderboard tiers, or custom number) configured in the match profile as the strategy arg.

![Matchmaking Team Formation Settings](/images/docs/matchmaking-team-formation-strategy.png)

### Backfilling
This setting tells the matchmaker if it should start a match the minute the min count has been reached. More players can join as long as the match is not full or the backfilling timeout has not been reached.
<Note>
  Presently, the backfilling rule does not work with **Relay** allocation.
</Note>

### Delay Partial Match

The `delay_partial_match_seconds` setting on a Match Profile controls how long the matchmaker should wait before creating a partial match (a match where the player count is between `min_players` and `max_players`).

When this setting is configured:
- If enough tickets are found to completely fill a match (`max_players`), the match is created immediately regardless of this setting.
- If the number of matching tickets is between `min_players` and `max_players`, the matchmaker will wait until the oldest ticket in the candidate set has been waiting for at least `delay_partial_match_seconds` before forming the match.
- This gives the matchmaker additional time to find more players and create fuller matches, rather than immediately settling for the minimum player count.

<Note>
  If `delay_partial_match_seconds` is set to `0` or left unset, partial matches are created as soon as the minimum player count is reached.
</Note>

## Allocation

The matchmaker snap has been integrated with the Snapser relay and game server fleet and lobbies snaps. While creating a match
profile you can select if you want the match to be allocated to your relay, a specific game server fleet or a lobby.

Additionally, you can also add metadata for your intended allocation destination. This metadata is a map of key-value pairs that you can use to pass additional arbitrary data to a lobby or fleet. For a Lobby, this
data will be passed into the Lobby's `allocation_metadata` field. For a Fleet, this data will be passed into the GameServer's annotations field, accessible via the Agones SDK.

### Derived Metadata

In addition to the static **Allocation Metadata** key-value pairs you configure on the profile, matchmaking can also forward **derived metadata** -- values that are not known at profile-creation time and are instead computed from the matched tickets when a match is formed.

You opt a rule into derived metadata from the [Custom String Rule](#custom-string) in your rule set:

1. Set Match Allocation to `fleet` or `lobby`.
2. Add a Custom String rule and leave the `Absolute` toggle **unchecked** so the rule runs in [relative](#relative-vs-absolute-rules) mode.
3. Check the **Append to metadata** checkbox on that rule.

When you do this, the Allocation section will show a read-only "Derived Metadata" preview listing the keys that will be populated. At match time, for each opted-in rule, matchmaking collects the values present on the matched tickets for that key and forwards them in the assignment metadata alongside your regular Allocation Metadata. For a Lobby allocation these arrive in the Lobby's `allocation_metadata`; for a Fleet allocation they arrive on the GameServer's annotations.

This is useful when the matched value cannot be hard-coded on the profile -- for example, the specific map a party requested, the language preference shared by everyone in the lobby, or the gamemode key that varied per ticket.

<Note>
  Append to metadata is only available on matchmaking snap version `1.10.0` and above, and only for relative Custom String rules when the allocation target is `fleet` or `lobby`.
</Note>

## Rules

- **Custom Tag**: Matches tickets that have the same custom tag.
- **Custom String**: Matches tickets that have the same custom string key and value pair.
- **Custom Number**: Matches tickets that have the same custom number key within a defined range.
- **Leaderboard**: Matches tickets that have the same leaderboard score within a defined range.
- **Statistics**: Matches tickets that have the same statistic value within a defined range.
- **Latency**: Matches tickets that have the same latency within a defined range (only applies to Titan allocation).

<a id="relative-vs-absolute-rules" />

<Note>
  Many of the Rules above support both a "relative" and "absolute" mode. In
  relative mode, the rule will be evaluated relative to the current ticket in
  the queue. Conceptually, this is equivalent to "Match this ticket with others
  of the same tier". In absolute mode, the rule will be evaluated based on the
  defined value in the profile: "Match tickets with tier='silver". You can
  toggle this behavior by clicking on the "Absolute" button in the rule.
</Note>

### Auto Expansion vs Manual Expansion

#### Auto Expansion

When creating a Match Profile, you can choose to enable Auto Expansion, instead of the legacy Manual Expansion steps. This way, the configuration for expansion is done only once per rule, instead of having to define multiple expansion steps.

When Auto Expansion is enabled, the matchmaker will automatically expand the search criteria over time. For Auto Expansion, the important fields to configure are:
- **Initial Range**: This is the value that the auto expansion will start from. For relative rules, this is the initial range around the ticket being evaluated. For absolute rules, there is an initial start and end value configured on the rule itself.
- **Spread Interval**: This is the rate at which the search criteria will be expanded, in seconds.
- **Spread Amount**: This is the amount by which the search criteria will be expanded at each interval. For example, if you set this to 10, then every `Spread Interval` seconds, the matchmaker will expand the search criteria by 10 `elo`.
- **Maximum Spread**: This is the maximum range for the rule.
- **Spread Strategy**: This is the strategy that the matchmaker will use to expand the search criteria. The options are `balanced`, `right` and `left`. The `balanced` strategy will expand the search criteria equally on both sides. The `right` strategy will only expand the search criteria on the right side. The `left` strategy will only expand the search criteria on the left side.

![Relative Auto Expansion](/images/docs/matchmaking-auto-expansion-relative.png)

The example above shows a relative number rule with auto expansion enabled. 

<Note>
  A Spread amount with the Balanced spread strategy will result in half the spread being added to the end of the range and half the spread subtracted from the start of the range. 
</Note>


![Absolute Auto Expansion](/images/docs/matchmaking-auto-expansion-absolute.png)

The example above shows an absolute rule with auto expansion enabled. Note the `initial_start` and `initial_end` values for the range. 

#### Manual Expansion

A common use case in Matchmaking is to allow users to expand their search criteria over time. For example, if a user is not 
able to find a match within 10 seconds, you may want to expand the search criteria to include users that are +/- 10% 
of the original search criteria. This is done by configuring the "expansion steps" for rules that support it.

In the example below, for the first 30 seconds, we want the match to accept users that are within +/- 10 `elo` of the ticket being evaluated.
Then, for the next 30 seconds, we want to expand the search criteria to include users that are within +/- 25 `elo` of the ticket being evaluated.
Note that the `applies_after` and `applies_for` fields define the window of time that the rule set is applied. You are free to add as many
expansion steps as you want. The matchmaker will evaluate the rules in the order they are defined in the rule set.

![Example Expansion Steps](/images/docs/matchmaking-expansion-steps.png)

The current set of rules that support expansion steps are:
- Relative Leaderboard Rules
- Relative Statistics Rules
- Relative Custom Number Rules
- Absolute Custom Number Rules
- Latency Rules

### Custom Tag

This is a tag that the user can define when creating a ticket. The Matchmaking snap will match tickets that have the same tag.

### Custom String

This is a key-value pair that the user can define when creating a ticket. The Matchmaking snap will match tickets that have the same key-value pair.

Custom String rules support both [relative and absolute](#relative-vs-absolute-rules) modes (matchmaking snap `1.7.0`+):

- **Absolute**: only tickets whose value for the configured key exactly equals the value on the profile will match.
- **Relative**: only tickets whose value for the configured key equals the value on the ticket being evaluated will match -- regardless of what that value is. Useful for "match me with others who picked the same thing" semantics (same map, same gamemode, same language preference, etc.) without enumerating every possibility on the profile.

When the rule is **relative** and Match Allocation is set to `fleet` or `lobby`, you can also check **Append to metadata** on the rule (matchmaking snap `1.10.0`+). The rule's key will then be added to the assignment's derived metadata at match time, with its value dynamically populated from the matched tickets. See [Derived Metadata](#derived-metadata) for details on how the data is forwarded to the allocation destination.

### Custom Number

This is a key, from and to value that the user can define when creating a ticket.
The Matchmaking snap will match tickets that have the same key and the value is within the defined range. This rule also
supports both absolute and relative modes.

### Statistics

Snapser users can define this integration via the `Statistics` rule while creating a Match Profile.

The Statistics rule supports two stat types:
- **Counter** (numeric): The stat value is treated as a number. Tickets are matched using range-based filters, and expansion steps / auto expansion can widen the acceptable range over time. The stat value is stored in the ticket's `double_args`.
- **String**: The stat value is treated as a string literal. Tickets are matched using exact equality -- only tickets with the same string value will match. The stat value is stored in the ticket's `string_args`. Expansion does not apply to string-type statistics.

#### Pre-requisites

1. Create a Statistic in the Statistics Snap. See ["How do I add a Statistic"](statistics#how-do-i-add-a-statistic-to-my-game) for more information.

### Latency

Matches are automatically allocated to the region based on the latency rule. The latency rule is a rule that specifies the acceptable latency for a match to be created. For example, if the latency rule is set to 100ms, then the match will be allocated in the region that has a sub-100ms latency for each player.

You can specify the desired latency range at the rule set level. This means that you can have different acceptable latency ranges for different game modes, as well as gradual matching that increases the acceptable latency range over time.

![Titan Latency Rule](/images/docs/matchmaking-latency-ruleset.png)

#### Get the Latency to a Region
In order to figure out the latency to a particular region, use the **GetPingUrls** endpoint to fetch the ping urls for each enabled region. You can use this endpoint to ping the region and get the latency.

<Note>
  The **GetPingUrls** endpoint (`/v1/matchmaking/pingUrls`) is the preferred way to fetch region ping URLs. The older **GetTitanUrls** endpoint (`/v1/matchmaking/titanUrls`) is maintained for backwards compatibility but GetPingUrls should be used for new integrations.
</Note>

<CodeGroup title="GetPingUrls API response" label="ping urls">
```
{
  "ping_urls": {
    "oregon": "https://relay-oregon-url.stratos.snapser.com/ping",
    "oregon-ga": "https://relay-oregon-ga-url.stratos.snapser.com/ping",
    "singapore": "https://relay-singapore-url.stratos.snapser.com/ping"
  }
}
```
</CodeGroup>

You can then ping each url and get the latency to that region, and then pass that latency to the `latency_args` field in the `CreateTicket` endpoint.

<Note>
  Use the keys exactly as they come back from the endpoint. A Snapend with
  [protected regions](/docs/infra/snaps/game-server-fleets#protected-fleet-regions) enabled
  returns `-ga` suffixed keys alongside the standard ones, and those suffixed ids are what
  `latency_args` expects. Do not strip the suffix.
</Note>

#### Create a Ticket with Latency
The Latency rule works in conjunction with a new field in the `CreateTicket` endpoint: the "latency_args". This field is specified during ticket creation and contains a map of each enabled region to that clients latency. Say most of your users are in North America and Asia, then the game client can pass a map of the latencies it has to the "Oregon" and "Singapore" regions. Say those are 50ms for Oregon and 100ms for Singapore. This will tell the matchmaking service that the client has a 50ms latency to the US region and a 100ms latency to the EU region. The CreateTicket payload will look something like this:

<CodeGroup title="CreateTicket API payload" label="latency args">
```
{
  "user_id": "123",
  "search_fields": {
    "latency_args": {
      "oregon": 50,
      "oregon-ga": 42,
      "singapore": 100
    },
    "tags": ["ranked"]
  }
}
```
</CodeGroup>

<Note>
  The keys are region ids, so a
  [protected region](/docs/infra/snaps/game-server-fleets#protected-fleet-regions) is keyed by
  its suffixed id — `oregon-ga`, not `oregon`. A standard region and its protected sibling are
  two separate entries with two separately measured latencies, and matchmaking will only
  allocate into a region your client supplied a latency for.
</Note>

<Note>
  We plan to simplify this process in the future by providing a built in sdk
  call that will ping each region and return the correct formatted latency map
  for you.
</Note>

## Rule Sets

A rule set is a collection of rules that are used to match users together. A match profile can have multiple rule sets, and matches can be created for each rule set. All rules within a rule set are ANDed together.
For each rule set, you can define its applicable **Duration**. This is relative to the ticket's creation time. For example, if you set the Duration to 60 seconds,
then the rule set will only apply to tickets created within the last 60 seconds. This is useful for defining fallback rule sets. See the examples below:

![Fuzzy Pic](/images/docs/matchmaking-fuzzy-1.png)
![Fuzzy Pic](/images/docs/matchmaking-fuzzy-2.png)

<Note>
  Only one rule set is being evaluated at a time. If a ticket is created within
  the last 10 seconds, then it will be evaluated against the first rule set.
  Once the ticket is older than 10 seconds, it will be evaluated against the
  second rule set. If the ticket is older than 30 seconds (10s from rule set 1 +
  20s from rule set 2), then it will not be evaluated against any rule set.
</Note>

## Host Selection Criterion

The Matchmaking Snap allows you to add an optional criterion for selecting a host amongst all the
matched users. The host selection criterion only works when you have at least one of the following rules
in any rule set:
1. Leaderboard rule
2. Statistics rule
3. Custom Number rule

Once you have at least one of the rules, you will be able to pick any one of them, and tell the
matchmaker if you want to pick the host who has the `min` or `max`:
1. Leaderboard score
2. Statistic value
3. Custom Number value

## Match Data

Once a match has been formed, the Matchmaking snap creates a **MatchData** object that represents the live state of the match. Match participants can query and update this data via the [GetMatchData](#matchmakinggetmatchdata-api) and [UpdateMatchMetadata](#matchmakingupdatematchmetadata-api) APIs.

The MatchData object contains the following fields:

| Field | Type | Description |
| ----- | ---- | ----------- |
| `match_id` | string | The unique identifier for the match |
| `host_id` | string | The user ID of the host player |
| `match_profile_id` | string | The Match Profile that was used to create this match |
| `region` | string | The region the match was allocated to |
| `statuses` | map&lt;string, Status&gt; | A map of user IDs to their readiness status (`UNKNOWN_STATUS`, `NOT_READY`, `READY`) |
| `teams` | map&lt;int32, UserIdList&gt; | A map of team indices to the list of user IDs on each team |
| `ticket_ids` | string[] | The ticket IDs that were matched |
| `metadata` | map&lt;string, string&gt; | Arbitrary key-value metadata associated with the match |
| `start_after_seconds` | int32 | Delay in seconds before the match should start |

### Updating Match Metadata

Any participant in a match can update the match's metadata using the [UpdateMatchMetadata](#matchmakingupdatematchmetadata-api) API. The new metadata keys are merged into the existing metadata. This is useful for coordinating match state between participants -- for example, tracking game settings, map selection, or other runtime configuration.

<Note>
  Only users who are participants in the match (present in the `statuses` map) can read or update the match data.
</Note>

## FAQs
### How many Match Profiles and rule sets should I have?

This depends on your game. Typically, you will have a different Match Profile for each **game mode** in your game. For example, if you have a 1v1 game mode and a 2v2 game mode, then you will have two Match Profiles. For example, the 1v1 Match Profile will have "1" for the `min_players` and `max_players` and might use [FIFO](#how-can-i-define-a-fifo-matchmaking-queue) matching, whereas the 2v2 Match Profile will have "2" for the `min_players` and `max_players` and may have a rule set that matches tickets based on the user's rank.

The amount of rule sets is also dependent on your game's requirements. However, it is important to understand how the rule sets influence the matching:

- Tickets need to satisfy all rules of a rule set in order to be eligible for a match.
- Tickets do NOT need to satisfy all rule sets in a profile to be eligible for a match. As long as the ticket satisfies one of the rule sets, it will be eligible for a match.

Conceptually, the rules within a rule set are "AND"ed together, whereas the rule sets within a profile are "OR"ed together.

### What order are tickets matched in?

Match Profiles by default will match tickets in a FIFO manner. If there are no other rule sets existing on a Match Profile, then the tickets will be matched in the order they were created.

### Okay, I have a Match Profile. Now what?

Now that you have a Match Profile, you can start creating tickets. A ticket is a request to match a user. It may contain custom attributes or simply a user's id,
depending on your match profile setup. To create a ticket, you can use the Matchmaking API or the Matchmaking SDK. Each ticket created will be continuously evaluated against the rule sets in the Match Profile.
If there are enough tickets that match the rule set, then a Match object will be created. Each ticket will be updated with the match id and the match object.

Redis, Postgres

### Service Dependencies

The Matchmaking service can be used without any other service dependencies to
support custom attributes matching. However, to support the Leaderboards &
Statistics rules, the Matchmaking service needs to be paired with the
