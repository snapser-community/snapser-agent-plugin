# Queues

The Queues snap lets your game hand off work to be processed reliably and in the
background, instead of doing everything inside a single player request.

Typical uses:

- **Smooth out spikes** — accept a burst of actions (match results, purchases,
  analytics events) instantly and process them at a steady pace.
- **Run work after the fact** — grant rewards, send notifications, or update
  another service without making the player wait.
- **Decouple your snaps** — one BYOSnap drops a message on a queue; another (or
  the queue itself) handles it.

You **create and configure queues once** in the Snapser Portal, then your
BYOSnaps **enqueue** and (for some queue types) **dequeue / acknowledge**
messages at runtime through the three simple APIs below.

<Note>
  Each snapend can have a **maximum of 3 queues**. Queues are created and edited
  in the Portal's Queues admin tool — see [Add a
  Queue](/docs/infra/snaps/queues/config-tools/add) for a walkthrough of every
  setting.
</Note>

---

## Concepts

A **queue** holds **messages** until they are processed.

A message is just a **body** (any string — usually JSON) plus optional
**attributes** (small key/value metadata). Each message you enqueue gets an
**id**.

Every queue has:

- A **type** — `standard` or `fifo` (ordering guarantee).
- An **action** — what happens to a message once it reaches the front of the
  queue: `pull`, `deliver`, or `emit`.

You pick these when you create the queue. They decide which of the runtime APIs
you use.

### Queue types

| Type | Ordering | Use it when |
|------|----------|-------------|
| `standard` | Best-effort order, high throughput | Order doesn't matter (analytics, fan-out notifications). |
| `fifo` | Strict first-in-first-out, one at a time | Order matters (e.g. sequential inventory or currency operations). |

<Note>
  FIFO trades throughput for ordering: messages are handed out one at a time and
  the next is not released until the current one is acknowledged.
</Note>

### Actions — what happens to a message

| Action | What it does | You call |
|--------|--------------|----------|
| `pull` | The queue holds messages; your BYOSnap pulls them on its own schedule. | `Enqueue`, then `Dequeue` + `Ack` |
| `deliver` | The queue pushes each message to one of your BYOSnaps over HTTP. | `Enqueue` only |
| `emit` | The queue publishes each message as a Snapser EventBus event. | `Enqueue` only |

With **deliver** and **emit**, the queue does the work of getting the message to
its destination — you only ever enqueue. With **pull**, you are in control of
consumption.

## APIs

The `Queues` snap exposes the following runtime APIs. They are **internal-only**
— there is no client SDK for them. Call them from your BYOSnaps, snap-to-snap
inside the snapend, by addressing the Queues snap directly at
`http://service-queues:8090/v1/queues` with the header **`Gateway: internal`**
(no API key needed for internal traffic).

The same endpoints are also reachable from a game client through your snapend
gateway — swap the host for your gateway URL and the `Gateway: internal` header
for an `Api-Key` (both `internal` and `api-key` auth are accepted). For example,
an enqueue from outside the cluster looks like:

```bash
curl -X POST "https://gateway.<env>.snapser.io/<snapend>/v1/queues/queues/reward-grants/messages" \
  -H "Api-Key: <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{ "body": "{\"userId\":\"u-123\"}" }'
```

The internal examples below are the common case for server-authoritative work.

| API Name | HTTP Method | API Description |
| -------- | ----------- | --------------- |
| [Enqueue a message](#enqueue-a-message) | POST | Enqueue a message onto a queue. Works for every queue type and action. |
| [Dequeue messages](#dequeue-messages) | GET | Long-poll for messages on a pull queue. |

### Usage

#### Enqueue a message

Add a message to a queue. Works for every queue type and action.

```http
POST /v1/queues/queues/{queue}/messages
```

Parameters:

| Parameter | In | Required | Notes |
|-----------|----|----------|-------|
| `queue` | path | yes | Queue name. |
| `Gateway` | header | yes | Pass `internal` for snap-to-snap calls. Use an `Api-Key` header instead when calling through the snapend gateway. |

Request body (`application/json`):

| Field | Type | Required | Notes |
|-------|------|----------|-------|
| `body` | string | yes | The message payload, as a string (usually JSON). Max 256 KB. |
| `attributes` | map\<string,string> | no | Optional message attributes returned to consumers. Up to 7 small key/value pairs. |
| `dedup_id` | string | no | **FIFO only.** Two enqueues with the same `dedup_id` within the dedup window are treated as one. Defaults to a SHA-256 of the body. Ignored for standard queues. |
| `recipients` | string[] | no | **Emit queues only.** Sets the emitted event's recipients (e.g. user ids for Hermes routing). Ignored for other action types. |

#### Dequeue messages

Long-poll for messages to process. Only valid on `pull` queues.

```http
GET /v1/queues/queues/{queue}/messages?max_messages=1&wait_time_seconds=20
```

Parameters:

| Parameter | In | Required | Default | Notes |
|-----------|----|----------|---------|-------|
| `queue` | path | yes | — | Queue name. |
| `max_messages` | query | no | 1 | How many to return at once (1–10). FIFO always returns at most 1. |
| `wait_time_seconds` | query | no | 0 | How long to wait for a message before returning empty (0–20). Use ~20 to avoid tight polling loops. |
| `Gateway` | header | yes | `internal` | Pass `internal` for snap-to-snap calls; use an `Api-Key` header through the gateway. |

#### Acknowledge a message

Tell the queue you've finished processing a message so it isn't delivered again.
Only valid on `pull` queues.

```http
DELETE /v1/queues/queues/{queue}/messages/{id}?receipt={receipt}
```

Parameters:

| Parameter | In | Required | Notes |
|-----------|----|----------|-------|
| `queue` | path | yes | Queue name. |
| `id` | path | yes | Message id being acknowledged. |
| `receipt` | query | yes | Receipt handle returned by dequeue. |
| `Gateway` | header | yes | Pass `internal` for snap-to-snap calls; use an `Api-Key` header through the gateway. |


A successful acknowledgement returns an empty object (`{}`).

If you **don't** acknowledge a message before the visibility timeout (see
below), it becomes available again and is redelivered. This is what makes
processing reliable: a crash mid-work means the message simply comes back.

#### The pull loop, in short

1. `Dequeue` (with a wait of ~20s).
2. For each message: do your work.
3. `Ack` it using its `receipt`.
4. Repeat.

## Reliability: timeouts, retries, and the dead-letter queue

- **Visibility timeout (~30s):** once a message is dequeued (pull) or an attempt
  starts (deliver), it's hidden from other consumers for this window. Ack within
  it, or the message is redelivered. This guarantees **at-least-once** delivery.

- **Retries & max attempts:** for `deliver`, a failed HTTP attempt (or an
  un-acked pull message) is retried. After **`max_attempts`** (default **5**),
  the message is moved to the queue's **dead-letter queue (DLQ)**.

- **Dead-letter queue (DLQ):** a holding area for messages that could not be
  processed. You can inspect, requeue, or delete them from the Snapser Portal.
  Nothing is silently lost.

- **`auto_ack` (at-most-once):** an optional per-queue setting. When on, a
  message is considered done the moment it's handed out (pull) or attempted
  (deliver) — no retries, no dead-lettering. Use it for fire-and-forget work
  where dropping the occasional message is acceptable. Default is off
  (at-least-once, with retries).

- **TTL (retention):** messages that sit unprocessed past the queue's TTL
  (default **4 days**) are discarded automatically.

## Queue settings reference

You set these in the Portal when creating or editing a queue. Name and type are
fixed once created (to change them, delete and recreate); everything else can be
edited later. See [Add a Queue](/docs/infra/snaps/queues/config-tools/add) for
the full tool walkthrough.

| Setting | What it controls | Default |
|---------|------------------|---------|
| **Name** | Unique queue name (letters, digits, `-`, `_`; up to 80 chars). | — |
| **Type** | `standard` or `fifo`. | `standard` |
| **Action** | `pull`, `deliver`, or `emit`. | — (required) |
| **Deliver target** | For `deliver`: the BYOSnap (`byosnap-<name>`) and HTTP path (`/v1/...`) to POST each message to. | — |
| **Max attempts** | Delivery attempts before dead-lettering. | `5` |
| **Queue TTL** | How long an unprocessed message is retained (60s–14d). | 4 days |
| **Message TTL** | Optional shorter per-message expiry. `0` = none. | none |
| **Dequeue rate** | Optional rate limit (messages/second + burst) for how fast messages are released. | unlimited |
| **Backlog limit** | Reject new enqueues once the backlog reaches this depth (back-pressure). `0` = no limit. | none |
| **Auto-ack** | At-most-once mode (see above). Pull and deliver only. | off |

## Choosing the right queue — quick guide

- **Process work yourself, in your own BYOSnap, on your own schedule?**
  → `pull` queue. Use `Enqueue` + `Dequeue` + `Ack`.

- **Hand each message to one of your BYOSnaps over HTTP automatically?**
  → `deliver` queue. Use `Enqueue` only; set the target BYOSnap + path.

- **Broadcast each message to other services / players via events?**
  → `emit` queue. Use `Enqueue` only; set `recipients` if routing to users.

- **Order matters?** Make it `fifo`. Otherwise `standard` for higher throughput.
