# Storage

Snapser's Storage Service makes it easy for games and apps to store any binary game
data in the cloud. In addition, the service handles data redundancy, scaling,
and, more importantly, concurrency control for the user's game or app blob. With the
Snapser storage service, you can rest assured that you are getting a highly
scalable, performant data store at your fingertips.

## Data Type

You can store any binary data. Structured or unstructured JSON data can be
saved in the cloud using the Storage service.

<Note>
  JSON is the most popular format for storing data in the cloud as it is easy to
  read, write, and parse.
</Note>

## Blob Types

The storage service comes with three types of blobs:

1. **Blob**: Blobs of data that can be replaced via an update.
1. **Append Blob**: Blob of data that can be appended to.
1. **Counter Blob**: Number Blob that can be incremented or decremented.
1. **JSON Blob**: A blob that can be updated using a JSON schema. This is a new feature that allows you to store data in a structured format. JSON blob also gives you the ability to do sub-document updates with full schema validation.

### JSON Blobs
JSON blobs allow you to store data in a structured format. Unlike a regular blob which treats the contents as a string, JSON blobs treat them as structured JSON entities.

#### Key Features
1. **Sub-document updates**: You can update a specific field in the JSON blob without having to replace the entire blob. This is useful for large blobs where you only need to update a small part of the data.
2. **Schema validation**: You can define a schema for the JSON blob and the storage service will ensure that all updates to the blob adhere to the schema.


#### JSON Schema
The [JSON schema](https://json-schema.org/) is a way to define the structure of the JSON blob. The schema is defined using a JSON object
that specifies the properties of the blob and their types. The schema is used to validate all updates to the blob.

<Note>
  By default, sub document updates are only validated for the fields that are being modified. This means that there are certain features of
  the jsonschema spec that are intentionally not supported in favor of performance. For example, the `anyOf`, `allOf`, `if/then`, etc are not supported. The reason for this is that these features require the entire document to be re-validated against the schema, which can be slow for large documents.
</Note>

In the configuration section, there is an optional boolean for `strict` validation of arrays. This tells the storage service to fetch the
array sub document, update it, and then validate it against the schema. This is useful for schemas that rely on validating the array in its
entirety. For example, if you have a schema that requires the array to be unique or of certain length, then you will need to set this to true.

#### Sub document updates

The sub document APIs - `UpsertSubDocument`, `GetSubDocument`, `DeleteSubDocument`, etc - all accept an object of the following format:

```json
{
  "value": "some_object",
  "path": "path.to.field"
}
```

The value can be any valid JSON object. The path is a dot separated string that specifies the location of the field in the JSON blob. The path can be nested and can contain arrays.

#### Example

The following example shows how fetch and update a subdocument JSON array using the storage service.

1. Create a json document
```
{
  "method": "POST",
  "url": "https://gateway.dev.snapser.io/{NAMESPACE}/v1/storage/owner/{OWNER_ID}/protected/json-blobs/{BLOB_KEY}",
  "payload": {
    "value": {
      "colors": [
        "red", "green", "blue"
      ],
      "season": "summer",
    }
  }
}
```

2. Fetch the `colors` array:
```
{
  "method": "GET",
  "url": "https://gateway.dev.snapser.io/{NAMESPACE}/v1/storage/owner/{OWNER_ID}/protected/json-blobs/{BLOB_KEY}/sub-documents/colors",
  "response": {
	"value": {
	  "colors": [
		"red", "green", "blue"
	  ]
	},
	"cas": "1744303876321378304"
  }
}
```

3. Update the `colors` array to append `yellow`:
```
{
  "method": "PUT",
  "url": "https://gateway.dev.snapser.io/{NAMESPACE}/v1/storage/owner/{OWNER_ID}/protected/json-blobs/{BLOB_KEY}/sub-documents/colors",
  "payload": {
	"updates": [{
	  "value": "yellow",
	  "path": "colors"
	}]
  }
}
```

4. Fetch the whole document:
```
{
  "method": "GET",
  "url": "https://gateway.dev.snapser.io/{NAMESPACE}/v1/storage/owner/{OWNER_ID}/protected/json-blobs/{BLOB_KEY}",
  "response": {
	"value": {
	  "colors": [
		"red", "green", "blue", "yellow"
	  ],
	  "season": "summer"
	},
	"cas": "1744303876321378304"
  }
}
```

Observe that the `colors` array has been updated to include `yellow`. The CAS value has also changed, indicating that the blob has been updated and the `season` field is unchanged.

### Dynamic Blobs
Occasionally, you may want to create many blob keys at runtime. For example, you may want to create
a blob for each user in a matchmade game, but can't configure those keys via the admin console beforehand.
To support this, we've added the concept of a *dynamic blob*.

![Dynamic Blob Toggle](/images/docs/dynamic-blob-toggle.png)

Dynamic blob keys are created the same way as regular blobs via the admin console. If you enable the
dynamic blob feature, the blob key will be treated as a prefix and the storage service will allow you
to create blobs with keys that start with that prefix.

The following example shows how serveral user blobs can be created for the same dynamic key:

1. Create the dynamic blob key named `season1` in the admin tool.
2. Use the BatchCreateBlob
```
{
  "method": "POST",
  "url": "https://gateway.dev.snapser.io/{NAMESPACE}/v1/storage/batch/blobs",
  "payload": {
    "value": {
      "blobs": [
		{
			"value": "blob #1",
			"owner_id": USER_ID_1,
			"blob_key": "season1-{USER_ID_1}",
			"access_type": "public"
		},
		{
			"value": "blob #2",
			"owner_id": USER_ID_2,
			"blob_key": "season1-{USER_ID_2}",
			"access_type": "public"
		}
	  ]
    }
  }
}
```

3. Once the blobs are created, Users 1 & 2 can now fetch or delete their blobs using the User auth API:

```
{
  "method": "GET",
  "url": "https://gateway.dev.snapser.io/{NAMESPACE}/v1/storage/owner/{USER_ID_1}/public/blobs/season1-{USER_ID_1}",
  "response": {
	"value": {
	  "blob #1"
	},
	"cas": "1744303876321378304"
  }
}
```

<Note>
  All write operations on dynamic blobs (insert, replace, update, increment) must use the batch operations API.
  This is to ensure that the keys are created in a controlled manner and to prevent accidental creation of too many blobs.
  Once a dynamic blob is created, you can use the regular APIs to read or delete the blobs.
</Note>

Dynamic blobs are supported for all blob types, including append blobs, counter blobs, and JSON blobs.

## Blob Access Control

Each blob can have one of the following access types during creation.

1. **Public**: Anyone can read or write to these blobs.
2. **Protected**: Anyone can read the blobs, but only the owners can write to the blobs.
3. **Private**: No one except the owners can read and write to the blobs.
   <Note>
     Most developers chose to use the protected blob type. Use the support
     channel if you want to discuss this topic further.
   </Note>

## Concurrency Control

The service provides concurrency control via **Check and Set** or **CAS**. Every blob in the storage service has an
associated CAS value.

### Check and Set (CAS) for Updates
Every time you update the blob, the CAS value changes and is returned in the response. Your client
can only edit the blob contents if the value of the CAS matches. This case is handy if your game or app supports multi-device play.

### Example
Say the same physical user A is playing your game on an iPhone and iPad. They pick up their iPhone and play the game. They then pick up the iPad. Your iPad client code tries to sync the data with the Storage service and realizes a CAS mismatch (because the game state progressed when the user played on the iPhone). Your game can then allow the user to continue from the same state as the iPhone or replace it with the iPad state.
This is how the storage service ensures you are not giving any surprises to your audience, and every blob update is happening in a way that guarantees concurrency control.

<Note>
  Passing CAS on updates is only required when you are using type: Blob. Its not
  required for append and counter blobs.
</Note>

### Check and Set (CAS) for Deletes

The `Delete API` for every blob takes an optional CAS parameter. This
ensures that you can safely delete the contents of the blob only if the CAS
matches.
