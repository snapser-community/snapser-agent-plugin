# Auth

Snapser's Auth Service allows you to drop authentication into your app in a
Snap. The service currently supports anonymous authentication, email
authentication, and third-party authentication like Apple, Epic, Facebook, Google, Steam, and Xbox.
After a successful authentication, the service returns the user Id and a token that your game or app client
can use to talk to your Snapser services.

It's not a bad idea to start the user in Anonymous auth to get them interacting with your game or app while navigating with your FTUE (First Time User Experience). 
Later on, you can prompt using a pop-up asking the user to secure their account
via email or the other third-party connectors, we support.

### Removing your connectors
You can remove any active connector from the Snaps Configuration tool.
It should be noted that the changes take effect immediately and so this should
be done with utmost caution. All active calls made to login, sign up or associate for
the connector will stop working, once the connector is removed.

## Associating Accounts

Snapser also allows games to associate the same user with multiple types of
auth. For example, an app can start a user under Anonymous auth, reducing the
friction for your users to start the app. But later in the app, you can have
an option for the user to connect to Facebook, Apple, etc. Snapser provides an
associate endpoint, allowing your game to link the anonymous and FB auth for
the user. Once you do this, the user can use either auth method to talk to
your Snapser services.

<Note>
  You can associate only one third-party login once. E.g., If you associated FB
  auth with an anonymous auth account. You cannot now associate the same FB
  account with another anonymous account.
</Note>

**IMPORTANT**: Snapser Authentication can be thought of as a keychain. The user can have multiple
keys to open the same lock. The lock here is your Snapser services.

## Authentication Tokens
Users are validated using a session token. This token is generated when the user logs in
and is used to authenticate the user for all subsequent calls to your Snapser services.
The token is valid for a certain period, after which the user will have to re-login.

### Auth Token Extension

Every authenticated user gets a token that is valid for a certain period.
It is important that your app client refreshes the token before it expires to ensure uninterrupted user experience.
If a token expires, the app client will have to re-login the user.

To give users a seamless experience, we recommend that the app client refreshes the token before it
expires. When the user logs in, the Auth snap sends back the following:
```
"session_token": "<user_token>"
"refreshed_at":"1726612234"
"token_validity_seconds":"2592000"
```
The app client should store or cache the `session_token` and `token_validity_seconds` in the app client.
The app client should then refresh the token before the `token_validity_seconds` elapse.

When you call the **Refresh Token** API, the Auth snap will return a new token with a new expiry time.
```
"session_token": "<new_user_token>"
"refreshed_at":"1726612310"
"token_validity_seconds":"2592000"
```
The app client should then follow the same process and refresh the token before the new `token_validity_seconds` elapse.

### App Token Expiry Testing
To test the token expiry, you can set the token validity to a very low value like 60 seconds in the dev or
staging environment. This will allow you to test the token expiry flows in your app client.

<Note>
The Session Management configuration tool allows you to control the session duration and invalidation settings.
</Note>
