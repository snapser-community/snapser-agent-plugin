# Remote Config

App clients often need dynamic configuration on startup to drive unique
experiences and setup features and scaffolding on app or game launch. For most apps
this can be a blocking call and so low latency is an absolute must. With the
Remote config snap you get a low latency performant service that delivers
studio defined app configuration to your clients. The service also supports
overrides at a per user or segment level, allowing you to deliver unique
experiences to different users.

## Remote Config Types
There are two types of remote configurations:
1. **App config**: This is the base configuration that is applicable to all users. Mainly controls game or app features and settings. You can use app configs for feature flags, TOS URLs etc. You can have multiple app configs, keyed by version.
2. **User config**: This is the configuration that is specifically for game/app users. You use user config for personalization. User configs have a concept of overrides that can be applied to a segment of users or to individual users.

<Note>
  Snapser recommends that this is the first API you hit post login or token
  refresh to setup your base configuration.
</Note>

## App configs
Game studio can setup their base remote configuration using the **App Config** admin tool. The tool takes a JSON representation of your
app config and allows you to enter a JSON schema validator to ensure that only a valid JSON as per the schema is accepted as a valid configuration.

### Base App Config

The base app configuration is nothing but a JSON that is applicable to the entire app.
This JSON is completely designed by the developer and Snapser
delivers it to the app client.

### Version

You can add multiple versions of your app config. This is useful when you want to
roll out a new version of your app configuration if you are making any non-backward compatible changes.

### Example

Consider you have the following base app configuration with version `v1`:

```
{
  "server_version": "1.0",
  "tos_version": '1.5',
}
```

Say you replaced your backend server with a new version and you want to update the configuration to reflect this change. You can create a new version of your app config with version `v2` and change your upcoming client build to point to this new version `v2`.:

```
{
  "server_version": "2.0",
  "tos_version": '1.5',
}
```
Eventually you can deprecate the old version `v1` and remove it from the snap configuration tool.

## User configs

Developers can setup their base remote configuration using the **User Config** admin tool.
The tool takes a JSON representation of your user config and allows you to enter a JSON schema validator to ensure that
only a valid JSON as per the schema is accepted as a valid configuration.

![Admin Pic](/images/docs/remote-config-admin.png)

### Base User Config

The base user configuration is nothing but a JSON that is applicable to all users.

### Overrides

Within the remote configuration snap, you have the ability to override
certain sections of your JSON base configuration. You also have the ability to
associate this override with all users or only a segment of users. Snapser
also allows you to slowly rollout your overrides, ensuring that you are
rolling out these changes safely and can monitor the impact of the changes.

As an example you may decide to add overrides for the following cases:
1. For users under level 5, you may enable a feature that shows helper style windows and guides in the app.
2. You may want to unlock features for highly engaged players in your app.
3. You may want to give a discount to users who have not made a purchase in the last 30 days.

### Audience
You can chose one of the following audiences for your override:

- **All Users**: Allows you to target your entire user base using overrides to provide the overridden configuration to deterministic portions of your base user config.
- **Segment**: Allows you to select one of your already configured segments to target.

For example, if you only want to target users with 100 or more logins, you can:
  - (Statistics Service) Create a User Statistic called "logins" and increment it when a user logs in.
  - (Statistics Service) Create a Segment that has a predicate that "logins" is equal to or greater than 100.
  - (Remote Config Service) Select that Segment in the Remote Config service when choosing the audience for your override.

### Sort Order

Users may be eligible for multiple overrides, that potentially modify the same
field in the configuration. To prevent conflicts, a sort order can be
specified for each override. Overrides are always applied in ascending sort
order.

### Testing

You can specify a comma separated list of user IDs for each override. The
override will be applied to the configuration of these users even if they are
not a part of the specified segment or ramp.

<Note>
  This is primarily meant to be used for game/app admins and QA to easily test out
  the game with specific overrides applied.
</Note>

![Override Pic](/images/docs/remote-config-admin-overrides.png)


### User Config Example

Consider you have the following base user configuration:

```
{
  "store": {
    "enabled": true,
    "discount": {
      "percentage": 10,
      "valid_until": "2023-01-05"
    }
  },
  "show_tutorial": false,
  "banner_content": "<h1>New Years Sale!</h1>"
}
```

Now say, you want to provide a bigger discount to a segment of users.
You can create a new override in your admin tool by specifying **store.discount.percentage** as the **Path** and **20** as the **Value**.

```
{
  "percentage": 20,
  "valid_until": "2023-01-10"
}
```

<Note>
  Overrides need to be a valid JSON as well. Also, the override will be checked
  to ensure that the resulting configuration is still valid according to the
  provided schema, for additional safety.
</Note>

Finally, you will have to select the audience to apply this override to. You can
either select **All Users** or a specific **Segment**.


## Tracking History

Remote config history maintains a version history of all configuration changes.
It encompasses modifications related to app-config, user-config, and overrides.
This history allows rollback to previous versions whenever needed and ensures that changes
can be tracked, analyzed, and reverted if unexpected issues arise.

### App Config History
Click on `App Config > History` to view the App Config history.
Select the config version to view the changes.

![App config history Pic](/images/docs/remote-config-app-config-history.png)

### User Config History
Click on `User Config > User Config History` to view the User Config history.
The User Config tool allows you to view the history of changes made to the user config.
If you have more than one saved user config, you will see a `Revert` button appear next to the version you want to revert to.
Once Reverted, a new version will be created with the reverted configuration and with the `Copy of` value populated with the version that was reverted from.

![User config history Pic](/images/docs/remote-config-user-config-history.png)

### Overrides History
Click on `User Config > Overrides History` to view the User Config history.
Select the override version to view the changes.
  ![Overrides history Pic](/images/docs/remote-config-overrides-history.png)

## Playground Tool

The **Playground** tool allows you to preview the configuration that would be
returned by the service for a given user or segment of users.
Using this tool you can specify one or more overrides to preview and visualize what the
resulting configuration would look like by applying those overrides.

![Playground Pic](/images/docs/remote-config-admin-playground.png)

## User Config Preview

The **Preview User Config** tool allows you to
see the configuration that would be returned by the service for a given user.
