# Trackables

The Snapser Trackables service enables your game or app to track a user's progress in your
game or other digital experience. This service supports adding various levels of progression based on a
numeric score.

## Concept

Plenty of games and social apps develop a structure for their level progression. This XP or energy
ends up being stored in a service like **storage**. While you can certainly go down that
route, any changes to the progression that your design team wants to control becomes
a nightmare to manage. The trackables service makes all this a breeze, especially for game or app dev teams.

## XP

XP is a numeric score that represents a player's progression in the game. 
The player progression can be represented in the form of levels. XP can be a single level or multiple levels.
{/* Incrementing the XP

The progression can be represented one dimensionally as a single score, or in the form of levels that the player can achieve.
The players XP can be incremented or decremented based on the player's
actions in the game.  */}

### Levels

Levels are nothing but numeric ranges that start and end at a
certain numeric score. Each XP can have one or more levels.

A final cap level can be created to represent the maximum level a player can achieve.

<Note>Overlapping levels and gaps in ranges are not supported.</Note>

### Auto Reset

When enabled, once all levels have been completed, the user's XP will be reset to 0. In case this setting is enabled then there cannot be a cap level

### Tracking

The game client needs to increment the XP score of the player based on the
player's actions in the game. The trackables service will automatically assign the level
to a user based on their XP score.

### Requirement
You can specify an optional requirement for starting a XP ladder. This allows you to chain your XP ladders,
essentially making one to be a requirement to complete before you can start a particular ladder.

<Note>
  Specifying a XP requirement is optional.
</Note>

### Scopes

Each XP supports the following scopes:

1. **External**: Progression visible from the client.
2. **Internal**: Progression visible only to Snaps within your cluster.

### Rewards
There are 2 types of rewards that can be setup for each level in a XP ladder:
1. **Level Completion Rewards**: These rewards are awarded to the user when they reach the end value of the current level.
2. **Level Up Rewards**: These rewards are awarded to the user when they reach the start value of the next level.

Each reward entry can be an Inventory Item, a Currency, a Drop Table, an Energy, or another XP. When granting an XP reward, you can pick any XP configured under Trackables, including the same XP that is being configured — this is useful for compounding progression or for boosting the current ladder from one of its own level thresholds.

When a Drop Table reward is granted, the result includes a `drop_index` — the zero-based index of the drop that was selected from the drop table's `drops` array. See [Drop Index](/docs/infra/snaps/inventory#drop-index) for details.
<Note>
  All rewards are optional and can be omitted.
</Note>

## Energy
Energy is a resource that is used to play a game. It is a finite resource that can be replenished over time.
This mechanic can be used to represent a player's stamina or lives in a game.

### Scopes

Each Energy supports the following scopes:

1. **External**: Visible from the client.
2. **Internal**: Visible only to Snaps within your cluster.

### Parameters
Each energy has the following parameters:
1. **Maximum energy**: Maximum energy that a user can have
2. **Time to recover**: Time taken to recover 1 energy

### Overflow
Some games allow the energy to overflow beyond the maximum energy. This can be enabled or disabled based on the game design.
<Note>
  If energy overflow is activated, replenish will only kick in when the energy drops below the maximum energy.
</Note>

## Streaks
Streaks track consecutive activity windows in your game or app — daily logins, weekly check-ins, completing a session every hour, even monthly streaks, and so on. A streak is composed of a `period_duration` (interpreted in a configurable `time_unit`) and a list of `rewards` granted at specific streak positions.

### Type
Streaks come in two flavors. The type is chosen at creation time and **cannot be changed**:

1. **Fixed**: Periods are anchored to a global schedule. Windows start at `offset_seconds` from UTC midnight (or at UTC midnight when no offset is given) and roll over when the period duration ends. Cooldown does not apply.
2. **Rolling Window**: Periods are tracked per user. A user can increment their streak as long as they do so before `period_duration` elapses; after that, a `cooldown_duration_seconds` must pass before the next increment is allowed.

### Time Unit, Period, Offset & Cooldown
- `time_unit` — the unit for `period_duration`. One of `seconds`, `minutes`, `hours`, `weeks`, `months`. Rolling Window streaks are locked to `seconds`.
- `period_duration` — the length of one window expressed in `time_unit`. Applies to both types.
- `offset_seconds` — *(fixed only)* shifts the global window relative to UTC midnight. **Always in seconds**, regardless of `time_unit`.
- `cooldown_duration_seconds` — *(rolling_window only)* the wait between increments. **Always in seconds**, regardless of `time_unit`.

### Length
- `max_length` — the highest streak position a user can reach. Set to `0` for no maximum. If non-zero, all reward positions must be less than or equal to this value.

### Rewards
A streak has a list of `rewards`. The list can be empty — a streak with no rewards is a valid, tracking-only configuration. If you do add entries, each one has a unique `rung_index` (the streak position at which the reward is granted), a `name`, optional `metadata`, and a `level_completion_rewards` payload that can include Inventory Items, Currencies, Drop Tables, Energy, or XP. Unlike XP, **a Streak cannot reward another Streak**.
<Note>
  Reward positions must be unique. If `max_length` is set, positions must be less than or equal to it. Each reward entry must contain at least one reward item — an entry with no items is rejected on save.
</Note>

### Scopes
Each Streak supports the following scopes:

1. **External**: Progression visible from the client.
2. **Internal**: Progression visible only to Snaps within your cluster.

### Behavior
1. **Loop on Complete**: When enabled, the streak restarts from position 1 once the final reward is reached.
2. **Repeatable Rewards**: When enabled, rewards are re-granted on every loop instead of only the first time the streak is completed. This setting only has an effect when `loop_on_complete` is enabled.

### Websocket Emitters

When [Web sockets](/docs/infra/snaps/hermes) are enabled on your snapends gateway, and you
have added the [Event Bus](/docs/infra/snaps/eventbus) snap, this snap can broadcast specific
events related to statistic and segments changes directly to the game clients. These events are
targeted to the appropriate user. Each event is uniquely identified by an enum, and the event
payload is a well-structured protobuf message. These protobuf messages can be downloaded from
the Downloads page.

You can choose to enable/disable events from the [Event Bus](/docs/infra/snaps/eventbus) configuration tool.

| Event Id | Event Name                         | Description                                            | Payload Proto Message                |
| -------- | ---------------------------------- | ------------------------------------------------------ | ------------------------------------ |
| 1        | TRACKABLES_XP_PLAYER_LEVELED_UP    | Published on user XP level up                          | EventTrackablesXpPlayerLeveledUp     |
