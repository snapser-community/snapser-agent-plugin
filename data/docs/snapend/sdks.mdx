# SDKs

With Snapser, each cluster you create comes with a customized SDK. Traditionally, developers have had to manage large SDKs, even when only a fraction of their functionality was needed. Snapser, however, crafts each SDK to include only the snaps you select, ensuring a lightweight, efficient experience with minimal memory usage.

Moreover, if you bring your own custom snap—be it a function, microservice, or monolith (BYOSnap)—to Snapser, our SDK can automatically integrate bindings for your code. Simply upload your OpenAPI 3.X `swagger.json` via our CLI tool, and your snap will be integrated seamlessly, saving your team valuable time and allowing you to focus on game development.

## Access Patterns

There are three primary ways to access your Snapser-powered backend (Snapend):

- **Client Access**: Devices running game code—Unity, Unreal, Roblox, Godot, Cocos, iOS, Android, Web—or custom engines in languages like C#, C++, Lua, Typescript, Go, Python, Kotlin, Java, Node.js, JavaScript, Perl, PHP, Closure, Ruby, Rust—connect directly to your Snapend.
- **Server Access**: External backend or game server code (using languages listed above) communicates with your Snapend.
- **Internal Access**: Your internal code, such as a private BYOSnap, can directly interact with other snaps within your Snapend.
- **Mixed Access**: Your code needs to make API calls across multiple auth types (user, api-key, and internal) from within a single codebase using a single SDK.

Let’s explore how the SDKs align with these access patterns.

## SDK Categories

So at a high level, Snapser provides five SDK categories:

### A. User SDKs

This category is designed for game client access. Except for a few public APIs—such as those for user login via the **Auth** snap—all other APIs require a valid JWT token. This token, generated by the **Auth** snap, must be included in each API call. The SDK will provide a parameter for passing this token seamlessly.

<Note>
  Use User SDKs from game clients to access Snapend APIs. These SDKs interact with your Snapend on behalf of your game users. Most User Auth SDK method calls will require a valid JWT user token. Only exceptions being public endpoints like user login.
</Note>

#### Where to download User SDKs
You need to go to the Snapend > Tools > Downloads page to download the User SDK.
There are two options:
1. **Game Client SDKs**: These are SDKs for game clients.
2. **Standard Language SDKs**: Use this widget to download a SDK for a custom game engine or programming language you are using on your client.

#### Using the User SDK
There is only one thing you need to keep in mind while using the User SDK:
1. **Special Parameter**: Every non-public API, SDK method will have a parameter called **token**. You need to pass the users JWT token as the value. The user JWT token is generated via the Login APIs exposed by the **Auth** snap.

### B. Api Key SDKs

This category is for your trusted server code. Api-Key SDKs do not require a JWT token; instead, they use an Api-Key, generated by the **Api-Auth > API Key Manager tool** within the **Auth** snap. This Api-Key must be included in each API call, and the SDK provides a parameter for it.

<Note>
  Use Api Key SDKs from any trusted server code to access Snapend APIs. These SDKs interact with your Snapend on behalf of your game. Meaning, they can hit Snapend APIs for any game users. Api-Key SDKs do not require a JWT token, instead, they use an Api-Key. You generate this Api key from the Configuration tool in the Auth snap.
</Note>

#### Where to download Api Key SDKs
You need to go to the Snapend > Tools > Downloads page to download the Api-Key SDK.
There is one option:
1. **Standard Language SDKs**: These are SDKs for any programming language you are using on your server. To generate the SDK, select SDK type: **api-key** and click **Generate**.

There is only one thing you need to keep in mind while using the Api Key SDK:

### C. Internal SDKs

Use this category for BYOSnaps within Snapend. No JWT token or Api-Key is required; instead, method calls take a parameter called **gateway** in each API call. To simplify, Snapser generates the environment variable **SNAPEND_INTERNAL_HEADER** that holds this  value **internal**, allowing easy integration without hardcoding.

<Note>
  Use Internal SDKs from BYOSnaps within Snapend. These SDKs interact with other snaps within your Snapend. Internal SDKs do not require a JWT token or Api-Key. Instead, they use a Gateway: Internal header. Additionally, you have to use Internal Snap URLs to access other snaps within your Snapend.
</Note>

#### Where to download Internal SDKs
You need to go to the Snapend > Tools > Downloads page to download the Internal SDK.
There is one option:
1. **Standard Language SDKs**: These are SDKs for any programming language you are using for your BYOSnap. To generate the SDK, select SDK type: **internal**, and hit **Generate**.

#### Using the Internal SDK
There are mainly two things you need to keep in mind while using the Internal SDK:
1. **Internal Snap URLs**: You need to use the Internal Snap URLs to access other snaps within your Snapend.
   Every Snapend that you create generates special environment variables that hold the URLs for each snap.
   **Example**: If you have a snap named **Inventory**, the environment variable **SNAPEND_INVENTORY_HTTP_URL**
   will hold the **Internal URL** for the Leaderboard snap including the port number. You should then override the
  base URL in the SDK with this environment variable to ensure your call is happening internally and not
  going out of the network and coming back in. This gives you a major performance boost.
2. **Special Parameter**: Every non-public API, SDK method will have a parameter called **gateway**. You need to pass **Internal** as the value. To make it easier, Snapser generates an environment variable called **SNAPEND_INTERNAL_HEADER** that holds the value **Internal**. Note, this tells the Snap within the Snapend that the call is coming from within the Snapend and not from an external source.


Here is an actual code example in Python:

### D. Unified SDKs

The Unified SDK is a single SDK that contains all APIs exposed across the **user**, **api-key**, and **internal** auth types. Unlike other SDK categories where the auth credential is passed as a parameter on every method call, the Unified SDK requires you to set the auth header once in the main constructor. After that, you simply call methods without passing auth credentials each time.

This SDK is ideal for developers who need to mix and match auth types within a single codebase while maintaining only one SDK.

<Note>
  Use Unified SDKs when your code needs to interact with your Snapend using multiple auth types (user, api-key, or internal) from a single SDK instance. Set the appropriate auth header once in the constructor and make method calls directly.
</Note>

#### Auth Headers

Depending on the access pattern you need, set one of the following headers in the constructor:

- **User auth**: `Token: $userSessionToken` — for calls on behalf of an authenticated user.
- **Api-key auth**: `Api-Key: $apiKey` — for trusted server-to-server calls.
- **Internal auth**: `Gateway: internal` — for BYOSnap-to-snap calls within your Snapend.

#### Where to download Unified SDKs
There are two ways to download the Unified SDK:
1. **Web App**: Go to your Snapend home page. Under both the **Client SDKs** and **Generic SDKs** sections, select `unified` as the SDK type and hit **Generate**.
2. **Snapser CLI**: Use the `snapctl snapend download` command with `--type unified`.

#### Using the Unified SDK
There are two things you need to keep in mind while using the Unified SDK:
1. **Constructor Header**: Set the auth header in the SDK constructor based on the access pattern you need. This replaces the per-method auth parameters found in other SDK categories.
2. **All APIs Available**: The Unified SDK exposes every API across all auth types, so you can call any method regardless of the auth type it was originally designed for.

Here is a code example in Python showing how to set up the Unified SDK with different auth types:

<CodeGroup title="Unified SDK Example">

## Legacy SDKs
Some of the existing Snapser customers will see an option to download Legacy SDKs. The new SDKs are more consistent and easier to use. We recommend that you move to the new SDKs as soon as possible.

<Note>
  With the new SDKs, all SDK categories have a consistent method naming convention. The method name is always in the format: `SnapId` followed by the `MethodName` This makes it easier to use and understand the SDKs.
</Note>


### Migrating from Legacy SDKs
#### A. Legacy User SDKs to new User SDKs
The main change we have made to the new user SDK is that it every API name has the Snap Id as a prefix.
**Example**: If you had a snap named **Profiles**, the old user SDK method to get the user profile was:
```csharp
GetProfileAsync(uId, SessionToken);
```
The new user SDK method will be:
```csharp
ProfilesGetProfileAsync(uId, SessionToken);
```
<Note>
Note, the prefix `Profiles` is **added** to the method name. This is to make it consistent with all our SDK categories.
</Note>

#### B. Legacy Api-Key SDKs to new Api-Key SDKs
The main change we have made to the new Api-Key SDK is that it we have dropped the SDK type to be part of the SDK method name.
**Example**: If you had a snap named **Profiles**, the old Api-Key SDK method to get the user profile was:
```python
api_instance.profiles_api_key_get_profile_with_http_info(user_id=req_id, api_key=YOUR_API_KEY)
```
The new Api-Key SDK method will be:
```python
api_instance.profiles_get_profile_with_http_info(user_id=req_id, api_key=
YOUR_API_KEY)
```
<Note>
Note, the `api_key` part is **dropped** from the method name. This is to make it consistent with all our SDK categories.
</Note>

#### C. Legacy Internal SDKs to new Internal SDKs
The main change we have made to the new Internal SDK is that it we have dropped the SDK type to be part of the SDK method name.
**Example**: If you had a snap named **Profiles**, the old Internal SDK method to get the user profile was:
```python
api_instance.profiles_internal_get_profile_with_http_info(user_id=req_id, gateway=os.environ['SNAPEND_INTERNAL_HEADER'])
```
The new Internal SDK method will be:
```python
api_instance.profiles_get_profile_with_http_info(user_id=req_id, gateway=os.environ['SNAPEND_INTERNAL_HEADER'])
```
<Note>
Note, the `internal` part is **dropped** from the method name. This is to make
it consistent with all our SDK categories.
</Note>


## Snapser CLI
You can use the Snapser CLI tool to generate SDKs for your Snapend. To download a Snapend SDK, you can use the following command:

<CodeGroup title="Download SDK">
```bash
# Download your Snapend SDK and Protos
# $snapend_id = Cluster Id
# $category = snapend-manifest, sdk, protos
# $format = One of the supported formats:
#   snapend-manifest(yaml, json)
#   sdk(unity, unreal, roblox, godot, cocos, ios-objc, ios-swift, android-java, android-kotlin, web-ts, web-js),
#   sdk(csharp, cpp, lua, ts, go, python, kotlin, java, c, node, js, perl, php, closure, ruby, rust),
#   legacy-sdk(unity, unreal, roblox, godot, cocos, ios-objc, ios-swift, android-java, android-kotlin, web-ts, web-js),
#   legacy-sdk(csharp, cpp, lua, ts, go, python, kotlin, java, c, node, js, perl, php, closure, ruby, rust),
#   protos(go, csharp, cpp, raw)
# $type = One of the supported types:
#   For category=sdk type=(user, server, internal, unified, app)
#   For category=protos type=(messages, services)
# $http_lib (optional) = One of the supported libs
#   For category=sdk format=unity http-lib=(httpclient, unitywebrequest, restsharp)
```

## Code Stripping
Game engines like Unity have a feature called **Code Stripping** that removes unused code from the final
build. This can sometimes cause issues with the Snapser SDKs. Some Unity versions require the following
link.xml to ensure there is no code stripping on the Snapser SDKs:

```xml
<linker>
  <assembly fullname="Snapser" preserve="all"/>
</linker>
```

<Note>
  If your Unity build is failing due to code stripping, update the link.xml under `src` folder with the above code.
</Note>
